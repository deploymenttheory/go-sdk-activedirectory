# Portable security descriptor implementation basis

SDK06 uses the existing `conditions` package for an owned binary codec and a bounded portable SDDL compiler/formatter. It does not evaluate effective access, resolve trustees, query claims, or call Windows conversion APIs at runtime. Windows APIs remain a separately exercised reference on supported Windows test hosts.

The binary representation follows [MS-DTYP SECURITY_DESCRIPTOR](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7d4dac05-9cef-4563-a058-f108abecce1d), [ACL](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/20233ed8-a6c6-4097-aafa-dd545ed24428), and [SID packet representation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/f992ad60-0fe4-4b87-9fed-beb478836861). Parse bounds are checked before indexing; original component order, aliases, padding, opaque ACEs, control and resource-manager bytes survive unchanged binary marshaling. Native-valid controls independently demonstrate nonzero reserved ACL bytes and unused capacity, so those fields are retained rather than interpreted or normalized away.

The text compiler follows [SDDL syntax](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/f4296d69-1c0f-491f-9587-a960b292d070). Conditional data uses the `artx` signature and postfix operators defined by [conditional ACEs](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/10dc22eb-788d-4343-b556-0b6969fe58ca), [literal tokens](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/d5818197-ebe9-4ac7-be3f-5182a9a577c9), [relational tokens](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/1711ff81-cf13-4870-919d-b91dca7e50de), and [logical tokens](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/6e92a8b3-60d8-4cc0-8441-dd6ba6e59e63). Resource attributes use [CLAIM_SECURITY_ATTRIBUTE_RELATIVE_V1](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/21f2b5f0-7376-45bb-bc31-eaa60841dbe9) and its [relative octet-string values](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/9020a075-c1af-4b03-930b-ba785743bcab).

SDDL is not a lossless encoding for every binary descriptor. Unknown ACEs, application-specific callback data and resource-manager control have no supported SDDL representation. Formatting refuses them explicitly while binary preservation/editing remains available. Absence, NULL and empty ACL states stay distinct. Domain-relative aliases need explicit caller SID context; no host-dependent alias expansion occurs.

Independent native references and exact generator sources are retained in [conditions/testdata](../../conditions/testdata/README.md). Full security-information selector `0x1ff` matters: selector `0x0f` filters resource attributes, mandatory labels and other non-audit SACL classes. The original filtered observations remain retained, with their scope explained. Native quirks are observations, not a blanket syntax oracle: the portable compiler accepts the documented signed minimum and rejects undocumented octet separators and negative unsigned resource literals; accepted canonical native forms still verify binary compatibility.

The reviewed `huner2/go-sddlparse` candidate at `94d4443c521193ad5c0e5c7929a7ddb63e48d1c0` was not adopted. Its decoded model rejects unknown ACEs and nonzero descriptor header byte data and reconstructs descriptor layout; it also introduces an ANTLR runtime. The SDK-owned codec avoids that dependency and keeps opaque binary preservation independent of SDDL representability.

Directory integrations preserve the section scope from the critical [LDAP SD-flags control](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/3888c2b7-35b9-45b7-afeb-b772aa932dd0). DACL-only reads do not establish that owner/group/SACL are absent. `Object.SecurityDescriptorSections` records explicit section selection, independently of whether values were returned. Portable/native controlled reads select GUID and uSNChanged with the DACL. The shared encoder preserves other components; resource editors retain inherited/unknown ACEs and change only recognized patterns. Actual TLS wire fixtures retain refusal/partial observations and accepted/uncertain write states without replay.

## Directory atomicity investigation

SDK06 remains incomplete. Derived OU/password-permission mutations now require a critical GUID/uSNChanged assertion from their own controlled snapshot, or the caller's explicit version. The assertion and DACL-only controls remain critical. A missing advertised guard stops submission; protected OU creation checks the guard before its Add. The separate gMSA retrieval descriptor uses exact-old whole-value delete/add and still needs its applicable live qualification.

The [native Server 2025 protocol probe](portable-security-descriptor-evidence/server2025-cas/index.json) tested a fresh marker/GUID-owned contact pair beneath an owned OU, using native .NET LDAP with Kerberos signing/sealing and critical SD-flags4. It did **not** execute the SDK. Both matching-old and deliberately stale-old `nTSecurityDescriptor` delete/add requests were refused with LDAP53 (`00002077`, `WILL_NOT_PERFORM`, data87). The independent fixture actor's ordinary replacement succeeded, establishing write permission. After-read proved rejected operations left the current DACL unchanged and retained the benign concurrent ACE. Independent [replicated cleanup](portable-security-descriptor-evidence/server2025-cas/replicated-cleanup.json) confirms both DCs have no owned fixture objects. Exact source, eleven stage journals, before/current/proposed/after bytes and SHA-256 hashes are retained. An earlier reference-tool enum-cast failure occurred before CAS submission; it is not evidence of SDK or protocol behavior.

The documented [AD extended-control inventory](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/3c5e87db-4728-4f29-b164-01dd7d7391ea) does not identify an assertion, transaction or per-ACE mutation control. SD-flags selects owner/group/DACL/SACL sections; unused bits must be ignored and do not select an ACE-level merge or precondition. Expected-entry-count monitors searches. Set-owner applies to Add. Notifications and DirSync report changes after the fact. These facts do not turn a read-before-write check into an atomic guard. [SD processing](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/e42f988c-72a0-4f8d-a705-7235eac175d9) also recomputes inherited ACEs from the parent at commit; client preservation is distinct from server inheritance behavior.

The ordinary descriptor-valued `msDS-GroupMSAMembership` attribute has a different demonstrated contract. Separate [native Server 2025 gMSA references](portable-security-descriptor-evidence/server2025-gmsa-cas/README.md) accepted the matching-old delete/add and refused the stale-old request with LDAP16, retaining the independently inserted concurrent ACE. The corrected Read Property fixture uses CommonAce mask `0x10`; a preceding Control Access `0x100` probe remains a distinct mechanics control. Both matching readbacks equal the proposed bytes, and both rejected readbacks equal the concurrent current value. Failed setup and invalid-ACE attempts remain retained with their original source and cleanup. These native probes never call the SDK, retrieve a password, create a KDS root key, or qualify effective permissions.

Owned portable TLS wire fixtures now invoke the public `UpdateServiceAccount` workflow, resolve the supplied reader SID, inspect the strict GUID-addressed old-value delete/new-value add in one Modify, and preserve owner/group/SACL/conditional/inherited/opaque data. Reader-only stale LDAP16 is classified as a concurrency failure while retaining the server status. Raw missing-value removal remains a separate LDAP16 error. Rejection, malformed/lost response, cancellation and partial readback retain their distinct states and observations; submitted uncertain requests are not retried. This verifies the actual portable adapter against owned protocol fixtures, not against AD.

No supported targeted LDAP alternative for `nTSecurityDescriptor` has yet been demonstrated. The refused delete/add strategy is not enabled for that special attribute, and unconditional replacement is not a fallback. The remaining work includes resolving that AD atomic-update constraint, qualifying the portable gMSA exact-old workflow against actual AD, and fresh Windows/Linux acceptance against Server 2016/2019/2022/2025. Local/native codec references and owned wire fixtures do not qualify that matrix. Issue171 must remain open until its complete scope and review gates are satisfied.
