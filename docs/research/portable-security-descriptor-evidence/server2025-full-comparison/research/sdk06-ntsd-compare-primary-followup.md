# SDK06: primary-source follow-up on nTSecurityDescriptor Compare and atomic Modify

Researched 2026-11-19. Scope: official Microsoft protocol/API documentation and LDAP RFCs; no LDAP, VM, SSH, or lab network calls were made. Runtime observations below were supplied by the parent task, not reproduced here.

## Finding

I did **not locate an explicit nTSecurityDescriptor-specific standalone LDAP Compare prohibition** in the primary sources reviewed. Microsoft explicitly documents only presence filtering for security-descriptor syntax, while also defining a binary security-descriptor comparison rule. These statements have different scopes. Neither the filter table nor the observed Compare diagnostic alone proves that an atomic Modify containing an old-value DELETE is universally unavailable.

## Established protocol facts

- `nTSecurityDescriptor` has `attributeSyntax: 2.5.5.15`, `oMSyntax: 66`, and `isSingleValued: TRUE`. This identifies String(NT-Sec-Desc), rather than ordinary String(Octet). The encoding is a binary SECURITY_DESCRIPTOR encoded otherwise like an octet string. [MS-ADLS §2.257](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adls/09aea023-3917-43f7-ba84-d0a574d2c649), [MS-ADTS §3.1.1.2.2.2.6](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/7c76697b-e654-42bd-8676-b8463787e030).
- MS-ADTS's supported-comparison table expressly concerns **LDAP search filters**. String(NT-Sec-Desc) maps to SecDesc; only `present` is marked supported. `equalityMatch`, approximate, ordering, substring, and the listed extensible matches are unmarked. [MS-ADTS §3.1.1.2.2.4](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/ad58bcc9-1ce3-4b4c-98b2-a79b62a39259).
- Separately, the SecDesc comparison rule delegates to Octet comparison: equality requires equal lengths and identical contents. This is a definition of comparison behavior, not a promise that every LDAP operation exposes it. The source calls this **SecDesc Comparison Rule**; no separate public LDAP `SecDescMatch` OID/API was established here. [MS-ADTS §3.1.1.2.2.4.9](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/5dcca0b6-169c-4f21-9392-8974ae5e4e1d), [Octet rule §3.1.1.2.2.4.7](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/b99c5ac7-7eec-4232-8048-3d39b761c055).
- AD does not expose its ordinary comparison rules as arbitrary extensible-match rules. An internal/comparison-rule name therefore cannot simply be supplied as a filter matching-rule identifier. [MS-ADTS §3.1.1.3.1.3.1](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/0bb88bda-ed8d-4af7-9f7b-813291772990).
- Standalone Compare evaluates an attribute's EQUALITY matching rule, returning compareTrue, compareFalse, or an error. [RFC4511 §4.10](https://www.rfc-editor.org/rfc/rfc4511.html#section-4.10). RFC4512 says an attribute type with no equality matching cannot support value assertions, including comparisons. Matching rules also determine which individual values Modify adds/deletes. **Conditional conclusion:** if a type lacks equality matching, the generic RFC restriction applies; the AD search-filter table alone does not establish every AD Modify matching behavior. [RFC4512 §2.5.1](https://www.rfc-editor.org/rfc/rfc4512.html#section-2.5.1), [§4.1.3](https://www.rfc-editor.org/rfc/rfc4512.html#section-4.1.3).
- RFC4517 distinguishes syntax/encoding from separately defined comparison semantics. Its octetStringMatch rule does not by itself assign that rule to the AD security-descriptor attribute. [RFC4517 introduction](https://www.rfc-editor.org/rfc/rfc4517.html#section-1), [§4.2.27](https://www.rfc-editor.org/rfc/rfc4517.html#section-4.2.27).

## What the supplied diagnostic establishes

Supplied observation: 12 native Compare requests without controls, across four owned OUs and expected SDs read with masks 4/7/15, returned LDAP 53 and `00002095: SvcErr: DSID-03080160, problem 5003, data 0`; zero CAS Modify requests were submitted. Full-mask reads reportedly returned 1864-byte descriptors with nonzero owner/group/SACL offsets.

LDAP 53 means unwillingToPerform. `0x00002095` is **ERROR_DS_GENERIC_ERROR (8341)**, a generic directory-service error. It is not a named NTSD comparison restriction. The earlier `0x00002077` is **ERROR_DS_ILLEGAL_MOD_OPERATION (8311)**. [RFC4511 Appendix A.1](https://www.rfc-editor.org/rfc/rfc4511.html#appendix-A.1), [MS-ERREF §2.2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/18d8fbe8-a967-4f1c-ae50-99ca8e491d2d), [Win32 numeric mappings](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--8200-8999-).

MS-ADTS makes the first eight diagnostic characters a hexadecimal extended error. Everything following them is informational debugging material; conformant implementations may omit it. Consequently `SvcErr`, DSID, problem 5003, and data 0 provide no portable normative NTSD-CAS conclusion. [MS-ADTS §3.1.1.3.1.9, Microsoft-hosted 2024 specification](https://winprotocoldoc.z19.web.core.windows.net/MS-ADTS/%5BMS-ADTS%5D-240610.pdf).

## Atomic Modify is a distinct question

One Modify's changes execute in order, atomically. DELETE specifies values to remove; REPLACE sets the resulting values. Intermediate modifications may violate some schema constraints; the completed entry must conform. An error response means no changes committed. [RFC4511 §4.6](https://www.rfc-editor.org/rfc/rfc4511.html#section-4.6).

For DC functional level WIN2003 or higher **without permissive modify**, AD requires absent-value removal to fail with `noSuchAttribute / ERROR_DS_CANT_REM_MISSING_ATT_VAL`. Duplicate insertion also fails. It separately requires schema compliance after Modify and additional NTSD constraints from §6.1.3. This supplies strict missing-value semantics, but does not explicitly guarantee NTSD DELETE support or define how a projected descriptor matches its complete stored value. [MS-ADTS §3.1.1.5.3.2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/76df255d-dc67-4c1f-adc6-1e5b60021304).

SD flags select read/write components; the documented default is 15. Update fields outside the mask are ignored. This does **not** document whether an old-value DELETE comparison is masked. Submitted inherited ACEs are ignored when computing the descriptor written; the DC recomputes inheritance and ensures consistency at commit. Thus byte normalization and projections must be investigated independently of standalone Compare. [MS-ADTS §6.1.3.2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/932a7a8d-8c93-4448-8093-c79b7d9ba499), [§6.1.3.3](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/e42f988c-72a0-4f8d-a705-7235eac175d9).

## Consequences for further validation (inference; not executed here)

- Stable independent complete mask-15 reads can establish that the expected bytes are reproducible. They do not establish server-side DELETE matching. A bounded actual strict `DELETE(expected complete SD) + REPLACE(new SD)` or `DELETE(expected complete SD) + ADD(new SD)` probe in **one** Modify can test that separate capability. A matching success and a valid stale-value rejection with unchanged post-state are both needed. Changing ADD to REPLACE does not itself remove a possible NTSD DELETE restriction. The earlier projected 1448-byte DELETE+ADD failure is not such a matching baseline.
- Standalone Compare must not be treated as a necessary proof oracle for strict Modify: it is a separate operation. Conversely, skipping it supplies no evidence that Modify CAS works. Malformed stale descriptors test validation, not stale-value matching.
- Permissive modify explicitly turns duplicate ADD and missing-value DELETE into success. A permissive `DELETE(expected)+REPLACE(new)` therefore loses the missing-old-value guard. [MS-ADTS §3.1.1.3.4.1.8](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/49cdb1e3-3baa-4c7c-8cde-7c26b13d3ba7).
- A permissive `ADD(expected)+REPLACE(new)` also has no established guard: matching ADD may become a no-op; stale ADD may temporarily introduce a different value before REPLACE. The specifications do not establish the eager single-value rejection this construction would need. Single-valued schema plus final schema validation cannot substitute for demonstrated stale rejection.

No finding authorizes weakening the SDK06 atomic-CAS/version contract, substituting a client read-check-write, treating LDAP53 as a stale conflict, or claiming universal NTSD CAS support/absence from this server's Compare results.
