# WinLDAP TLS and AD LDS connection contracts

Research date: 2026-11-12. Scope: SDK ticket #11; native Windows amd64/arm64 execution, portable configuration, explicit AD LDS endpoint/partition, LDAPS, StartTLS, and SIMPLE authentication. Initial audited SDK base: `131e418`; bindings: `v0.6.1-0.20261112134443-9f51cb95639f`. The callback correction below uses `v0.6.1-0.20261112154045-0e26232f901c` ([upstream PR #68](https://github.com/deploymenttheory/go-bindings-win32/pull/68)). This is a contract/source audit with a network-free native option check, **not evidence of successful lab qualification**. It supplements [connection](winldap-connection.md), [explicit credentials](winldap-explicit-credentials.md), and [lab provisioning](ad-lab-provisioning.md) research.

**Implementation decision:** use WinLDAP/Schannel automatic server-certificate validation with explicit Schannel flags, no server-certificate callback, and no public trust-bypass setting. Install one process-wide client-certificate callback that returns false, before setting those flags: native testing established that WinLDAP otherwise replaces `NO_DEFAULT_CREDS` with `USE_DEFAULT_CREDS`. Validate the resulting transport with actual untrusted, expired, and wrong-name peers before claiming ticket acceptance. A custom server-certificate validator is not required merely to enable ordinary Windows trust validation; its additional ownership and policy responsibilities are documented below for a future need. Mandatory online revocation checking is not added by this ticket.

**Evidence boundary:** Microsoft's WinLDAP session-options documentation establishes its connection to Schannel automatic validation. Schannel documents target-name checking. The inspected primary sources do not explicitly specify the exact string WinLDAP passes as Schannel's target for every DNS-alias/IP case. Consequently, correct matching against the SDK's single configured endpoint is an inference requiring native negative tests, not an unconditional documented guarantee.

## Automatic validation: supported contract and limits

`LDAP_OPT_SCH_FLAGS` accepts `SCHANNEL_CRED.dwFlags`. WinLDAP automatically selects automatic/manual credential validation and default-client-certificate behavior according to the installed client/server certificate routines. The option exists to customize Schannel behavior. This directly connects WinLDAP's callback selection to Schannel validation; it is stronger evidence than assuming that any encrypted socket is authenticated. [Microsoft session options](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/session-options).

Schannel automatically verifies the server certificate unless manual validation is requested. Its manual-validation guidance identifies the required checks: trusted complete chain, validity periods, usage, revocation, constraints, and server identity. These general requirements do not establish that every application enables online revocation retrieval. [Schannel authentication](https://learn.microsoft.com/en-us/windows/win32/secauthn/performing-authentication-using-schannel), [manual-validation requirements](https://learn.microsoft.com/en-us/windows/win32/secauthn/manually-validating-schannel-credentials).

Recommended SDK flags, set after installing the client-certificate decline callback and before connection establishment:

```text
SCH_CRED_AUTO_CRED_VALIDATION | SCH_CRED_NO_DEFAULT_CREDS | SCH_USE_STRONG_CRYPTO
0x00000020                  | 0x00000010                 | 0x00400000
= 0x00400030
```

Automatic validation is the Schannel default. `NO_DEFAULT_CREDS` prevents unsolicited client-certificate selection; it does not disable LDAP password authentication. `STRONG_CRYPTO` suppresses known weak cryptography. Do not set `MANUAL_CRED_VALIDATION`, `NO_SERVERNAME_CHECK`, `USE_DEFAULT_CREDS`, or revocation-ignore bits. The name-check opt-out explicitly disables comparing the supplied target against certificate names. [SCHANNEL_CRED flags](https://learn.microsoft.com/en-us/windows/win32/api/schannel/ns-schannel-schannel_cred).

WinLDAP's documentation does **not** specify the timing or merge/overwrite precedence of its automatically managed flags. Native, network-free testing on 2026-11-12 (reported Windows version `10.0.26300.0`, Wldap32 file version `10.0.26100.8457`) resolved the client-credential behavior: without a client-certificate routine, both `ldap_initW` and `ldap_sslinitW` immediately read back `0x00400060` after setting `0x00400030`. An independent .NET P/Invoke probe reproduced that behavior; installing a false-returning `QUERYCLIENTCERT` before setting the flags retained `0x00400030`. Installing it afterward changed the previous readback from `0x00400060` to `0x00400030`. This distinguishes WinLDAP's callback-dependent flag management from a numeric-option marshaling defect. The SDK installs the callback first and retains the original strict post-handshake policy; it does not accept the substituted default-credential flag. These checks did not connect to a server and do not establish certificate-validation behavior.

The native `QUERYCLIENTCERT` contract explicitly permits returning false to request anonymous TLS client credentials. Use one lazy process-wide cdecl callback with no captured state, retain it through all connection lifetimes, and never install a permissive server-certificate callback. Read back `LDAP_OPT_SCH_FLAGS` before and after connection during qualification; reject observed manual-validation/name-bypass settings. Readback is a useful consistency check, not independent proof of the underlying security context. Avoid silently OR-ing unknown process defaults into this closed SDK policy. [Microsoft client-certificate callback](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nc-winldap-queryclientcert), [.NET callback-by-value adapter](https://github.com/dotnet/runtime/blob/main/src/libraries/Common/src/Interop/Windows/Wldap32/Interop.Ldap.cs#L62).

Schannel's `InitializeSecurityContext` uses its target name to verify the server certificate. For this SDK, use one validated FQDN/IP, retain the explicit port separately, and disable DC discovery, referrals, and reconnect. Do not replace the expected identity with a server-returned `dnsHostName`. Test a DNS alias resolving to the same address but absent from the certificate, an IP endpoint without an IP SAN, and a valid DNS SAN endpoint. The exact WinLDAP-to-Schannel target mapping remains the qualification gap identified above. [Schannel target-name contract](https://learn.microsoft.com/en-us/windows/win32/secauthn/initializesecuritycontext--schannel).

**Revocation:** this proposal sets no `SCH_CRED_REVOCATION_CHECK_*` flag and no ignore flag. Do not advertise guaranteed online revocation checking or guaranteed fail-closed behavior for offline CRLs. The three explicit revocation scopes are mutually exclusive; enabling one later is a separate behavior change that needs retrieval, offline, missing-information, revoked, and timeout tests. A stricter optional policy is not necessary to satisfy this ticket's trust/expiry/name cases. [Schannel revocation flags and error handling](https://learn.microsoft.com/en-us/windows/win32/api/schannel/ns-schannel-schannel_cred#remarks).

**Protocol version:** `STRONG_CRYPTO` is not a portable assertion that TLS 1.2 is the minimum. Microsoft's cipher tables still associate some allowed suites with TLS 1.0/1.1, and the effective policy varies by OS. If the SDK promises TLS 1.2+, enforce that promise by checking the negotiated protocol before bind, not merely by setting this flag. [Windows cipher policy](https://learn.microsoft.com/en-us/windows/win32/secauthn/tls-cipher-suites-in-windows-server-2025).

After successful TLS setup, query `LDAP_OPT_SSL` and `LDAP_OPT_SSL_INFO`. Microsoft's example uses the former to detect SSL protection at runtime and the latter for connection security information. A set SSL option before the handshake is configuration, not proof of completion. `SecPkgContext_ConnectionInfo` supplies actual protocol and cipher strength; known client protocol values include TLS 1.2 `0x800` and TLS 1.3 `0x2000`. Require successful handshake and successful post-handshake checks before submitting credentials. [WinLDAP SSL example](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/example-code-for-establishing-a-session-over-ssl), [connection-info fields](https://learn.microsoft.com/en-us/windows/win32/api/schannel/ns-schannel-secpkgcontext_connectioninfo).

`LDAP_OPT_SSL_INFO` writes into a **caller-owned inline structure**: the Microsoft example passes `&sslInfo`; .NET pins its connection-info object and passes that address. Do not pass a pointer-to-pointer or free this Go-owned structure with `ldap_memfree`. The SDK also requires `DwCipherStrength >= 128`; this field reports the bulk cipher strength in bits, independently of the protocol identifier. [Microsoft example](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/example-code-for-establishing-a-session-over-ssl), [.NET Windows option adapter](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/Interop/LdapPal.Windows.cs#L34), [connection-info fields](https://learn.microsoft.com/en-us/windows/win32/api/schannel/ns-schannel-secpkgcontext_connectioninfo).

**StartTLS getter gap:** the sources inspected do not explicitly promise that `LDAP_OPT_SSL` becomes true after StartTLS; .NET does not check that getter after its upgrade. For StartTLS, successful `ldap_start_tls_sW` plus successful `SSL_INFO` reporting an acceptable actual protocol/cipher is the supported gate. Record the SSL getter during native qualification before requiring it to be true on this path. Direct LDAPS can require the configured SSL flag as well. [.NET StartTLS flow](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.cs#L504).

## Sequencing, waits, and ownership

| Mode | Native sequence before authentication |
| --- | --- |
| Existing protected Negotiate | `ldap_initW`; LDAPv3 and existing single-endpoint/session options; signing and sealing; connect; Negotiate bind. |
| LDAPS | `ldap_sslinitW(host, explicitPort, 1)`; LDAPv3/session/Schannel options; `ldap_connect` with timeout; verify negotiated TLS state; bind. |
| StartTLS | `ldap_initW(host, explicitPort)`; LDAPv3/session/Schannel options; `ldap_connect`; `ldap_start_tls_sW`; verify negotiated TLS state; bind. |

`ldap_sslinitW` creates the LDAP connection block and accepts an explicit port; nonzero `secure` selects TLS independently of the port. A failed allocation returns NULL, with `LdapGetLastError` supplying the LDAP error. Every allocated handle belongs to the caller until `ldap_unbind`, including failures. Do not infer LDAPS only from port 636: AD LDS custom SSL ports are ordinary inputs. [ldap_sslinitW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_sslinitw).

`ldap_connect` is the explicit network establishment step and accepts an `LDAP_TIMEVAL`; success leaves an anonymous connection. Keeping connect separate from bind distinguishes transport failure from authentication failure. Unbind after a failed connection as well as normal completion. [ldap_connect](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_connect).

StartTLS requires no existing TLS, signing, sealing, pending bind, or outstanding request. It performs both the LDAP extended operation and TLS negotiation. Its direct return is the client status; on `LDAP_OTHER`, retain `ServerReturnValue`. A referral may be returned, but is not chased. Automatic referral chasing/reconnect are disabled after the call. Pass nil controls; free any returned `LDAPMessage` on every path. Its documented default timeout is approximately 30 seconds, spanning the extended-operation response and handshake; there is no timeout argument. [ldap_start_tls_sW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_start_tls_sw), [message release](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_msgfree).

Do not enable the existing `LDAP_OPT_SIGN`/`LDAP_OPT_ENCRYPT` options on TLS sessions: these SASL protections cannot be combined with SSL. Do not implement StartTLS using a bare extended-operation request followed by bind; that would omit WinLDAP's transport upgrade. Do not stop TLS to recover from failure; close the handle. [Microsoft signing/sealing options](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_set_optionw), [StartTLS lifecycle](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/using-start-stop-tls-encryption).

**Cancellation contract:** retain synchronous calls on the calling locked OS thread. Check context before each native stage and immediately after return, and do not start bind after cancellation/TLS failure. There is no documented cancellable StartTLS handle or guarantee that `LDAP_OPT_TIMELIMIT` bounds its complete handshake; the bind documentation only specifies that option for each bind-response roundtrip. Do not promise an aggregate context deadline or close an in-use native handle from a competing goroutine. Native certificate retrieval can also add waits. [bind timeout](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_simple_bind_sw), [Go OS-thread locking](https://pkg.go.dev/runtime#LockOSThread).

## SIMPLE is a different credential representation

For `LDAP_AUTH_SIMPLE`, `ldap_bind_sW` consumes a null-terminated password string, and its `dn` argument is the server-accepted bind name. The same entry point consumes an identity structure for explicit Negotiate; do not pass that structure to SIMPLE. NULL credentials do not mean current Windows identity for SIMPLE. Calling this method is equivalent to `ldap_simple_bind_sW`. [ldap_bind_sW method contracts](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bind_sw).

SDK policy should require explicit, nonempty bind name and password, forbid a separate domain field for SIMPLE, preserve the name/password unchanged, and reject embedded NUL/invalid UTF-8 before native conversion. Submit credentials only after successful validated TLS. Keep mutable UTF-16 password storage alive through synchronous bind, then wipe/unpin it using the existing credential-owner discipline. The corrected `Ldap_bind_sW` can consume that buffer directly; `Ldap_simple_bind_sW(*string)` would create a hidden converted password copy. The release-after-return inference and limits on erasing Go strings are documented in [the credential lifetime audit](winldap-explicit-credentials.md).

An empty password is dangerous independently of TLS. AD LDS's `DenyUnauthenticatedBind` defaults to zero; setting it to one rejects a zero-length SIMPLE password. Therefore a successful zero-password response cannot be treated as proof of authenticated identity. Enforce the rejection locally regardless of server policy. `RequireSecureSimpleBind` is another server setting, also documented with default zero; the SDK must enforce TLS itself. [MS-ADTS configurable settings](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/41cbdb2c-eab1-45b0-8236-ae777b1c5406).

AD LDS accepts an object's DN and its explicit `userPrincipalName`, with UPN matching tried last. It also defines canonical-name, GUID, display-name, and SID mappings; these do not justify rewriting user input. `DOMAIN\sAMAccountName` and generated domain-UPN mappings are AD DS-only in this algorithm. Recommend DN for deterministic fixture/example identities. [MS-ADTS SIMPLE name forms](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/6a5891b8-928e-4b75-a4a5-0e3b77eaca52).

An AD LDS principal or bind proxy supports SIMPLE. Computer/domain principals authenticate to AD LDS using the specified SASL mechanisms rather than SIMPLE. Thus a valid Windows domain password is not by itself a valid native-LDS SIMPLE fixture. Preserve the existing Negotiate path for Windows identities. [MS-ADTS principal mechanisms](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/89ea294a-5b65-47bc-8ed5-51cc925858a7).

## AD LDS capabilities and partition selection

The distinguishing RootDSE capability is `1.2.840.113556.1.4.1851` (`LDAP_CAP_ACTIVE_DIRECTORY_ADAM_OID`); AD DS advertises `1.2.840.113556.1.4.800`. Generic version/integrity capabilities are shared and do not identify AD DS. Preserve unknown capabilities and represent unknown/inconsistent directory type explicitly; use the typed result for precise AD DS-only rejection. [MS-ADTS capability table](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/3ed61e6c-cfdc-487d-9f02-5a3397be3772).

AD LDS omits `defaultNamingContext` if its `nTDSDSA.msDS-DefaultNamingContext` is unset. It can still expose application, configuration, and schema naming contexts. An explicit partition should take precedence; otherwise require a usable default and report its absence rather than choosing the first context. Validate existence through an authenticated base-object read, preserve native no-such-object/referral/access errors, and never silently select another partition. These selection rules are SDK policy; absence of a default is documented server behavior. [MS-ADTS defaultNamingContext](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/c1ad47fb-e4a1-4240-a749-b8f07ee0ae91).

## Binding audit and native diagnostics

The pinned generated wrappers already provide the required additional exports: `ldap.Procs.Ldap_sslinitW` and `ldap.Procs.Ldap_start_tls_s`. The latter intentionally dispatches **`ldap_start_tls_sW` despite lacking a W suffix in its Go name**. Its server status and message are correctly pointer-valued, and W controls are correctly double pointers. Probe selected exports before allocation; retain existing cleanup probes. No new raw syscall is necessary for the automatic-validation route. [Pinned LDAP wrappers](https://github.com/deploymenttheory/go-bindings-win32/blob/9f51cb95639f/bindings/win32/networking/ldap/ldap_functions.go#L2681).

The client-certificate correction needs a typed binding helper in addition to those exports. The generic `Ldap_set_optionW` takes `unsafe.Pointer`, whereas `QUERYCLIENTCERT` is a callback code address represented by `uintptr`. The new generated `Ldap_set_client_certificate` adapter passes that word directly to the existing `ldap_set_optionW` export with `LDAP_OPT_CLIENT_CERTIFICATE`, without converting it to a Go data pointer or passing `&callback`. Its generator regression checks this dispatch and that helper emission does not inflate native API coverage; its native test retrieves the exact installed callback address and checks policy readback, including removing/reinstalling the callback. SDK code uses that generated adapter; it contains no raw syscall workaround. This correction still requires live TLS qualification after the dependency update.

Schannel flags are typed constants in `security/authentication/identity/identity_enums.go`, and `identity.SecPkgContext_ConnectionInfo` has seven 32-bit fields. `LDAP_OPT_SCH_FLAGS`, `LDAP_OPT_SSL`, and `LDAP_OPT_SSL_INFO` are projected. Existing option APIs accept `unsafe.Pointer` and preserve caller storage. The audited TLS signatures show no blocking pointer-conversion defect. [Pinned identity enums](https://github.com/deploymenttheory/go-bindings-win32/blob/9f51cb95639f/bindings/win32/security/authentication/identity/identity_enums.go), [structures](https://github.com/deploymenttheory/go-bindings-win32/blob/9f51cb95639f/bindings/win32/security/authentication/identity/identity_structs.go), [LDAP constants](https://github.com/deploymenttheory/go-bindings-win32/blob/9f51cb95639f/bindings/win32/networking/ldap/ldap_constants.go).

Preserve direct LDAP status, operation, StartTLS server status where applicable, and any available extended native details before unbind. `LDAP_OPT_SERVER_EXT_ERROR` returns a numeric Win32 server error; `LDAP_OPT_SERVER_ERROR` returns diagnostic text. These are not documented to expose a Schannel HRESULT for every client-side certificate failure. Do not equate generic server-down/connect failure with a specific certificate defect. [Session error options](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/session-options).

If collecting `LDAP_OPT_SERVER_ERROR`, copy its W string and free the original allocation with the corrected `Ldap_memfreeW`. `LDAP_OPT_ERROR_STRING` and `LDAP_OPT_HOST_NAME` are explicitly borrowed exceptions and must not be freed. Bound/sanitize diagnostic text and avoid printing credential/configuration objects. Numeric statuses must survive even when detail retrieval fails. [ldap_get_optionW ownership](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_get_optionw).

## If custom certificate verification becomes necessary

This is an alternative design, not a requirement for the selected automatic path. Registering a server callback switches responsibility to the callback; returning true unconditionally defeats validation. The callback receives `**CERT_CONTEXT`, not a leaf pointer directly. Free the supplied `*CERT_CONTEXT` using `CertFreeCertificateContext` before returning, including rejection. Return false on missing state, nil pointers, validation error, or panic. [VERIFYSERVERCERT contract](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nc-winldap-verifyservercert).

The native callback is `cdecl`. .NET passes its delegate **by value** to `ldap_set_optionW`; the option receives the callback code address, not the address of a Go integer containing that address. Its setter only installs the native routine when an application callback is supplied, corroborating default reliance on native validation. [Microsoft SDK callback declaration](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/Winldap.h#L2990), [.NET interop](https://github.com/dotnet/runtime/blob/main/src/libraries/Common/src/Interop/Windows/Wldap32/Interop.Ldap.cs#L64), [.NET callback setter](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.cs#L454).

Use one process-wide callback and a synchronized native-handle-to-validator registry. Go callback allocations are never released and only a limited number are supported; per-Dial capturing callbacks leak those resources. Keep each registry entry through `ldap_unbind`, avoid holding its lock across native calls, and require observed successful verification before bind. Pin any nested Go input buffers for native calls. Native sources do not promise callback-thread affinity; do not infer it from a successful local observation. [Go callback contract](https://github.com/golang/go/blob/go1.25.0/src/syscall/syscall_windows.go#L228), [Go Pinner](https://pkg.go.dev/runtime#Pinner).

A complete native validator would build a chain with `CertGetCertificateChain`: current time, chosen Windows chain engine, the certificate's additional store, and Server Authentication EKU. Free its returned chain with `CertFreeCertificateChain`. Explicit revocation checking requires an appropriate chain-build flag; policy checking alone does not fetch/check revocation. To bound revocation retrieval use `CERT_CHAIN_REVOCATION_ACCUMULATIVE_TIMEOUT` plus `CERT_CHAIN_PARA.dwUrlRetrievalTimeout`, understanding that this is not an aggregate context deadline. [chain creation](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain), [chain parameters](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_chain_para).

Then call `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_SSL, ...)`, with correctly sized structures, `AUTHTYPE_SERVER`, the configured hostname, and zero ignore flags. Require successful API invocation, zero policy `DwError`, and acceptable chain trust status. A true return alone means the check ran, not that the certificate is valid. [policy API](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certverifycertificatechainpolicy), [SSL policy fields](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-httpspolicycallbackdata).

Bindings expose the needed Crypt32 functions and the correct double-pointer callback shape. One integration hazard remains: the policy wrapper takes `foundation.PSTR`, while `CERT_CHAIN_POLICY_SSL` is the native integer-resource value `uintptr(4)`. Avoid an unchecked integer-to-Go-pointer workaround merely to reach that API; an upstream integer-policy helper would be preferable if this route is selected. The callback comment recommends `NewCallback`; the native header specifies cdecl, so use the appropriate calling convention even though the supported 64-bit ABIs avoid the 32-bit stack-cleanup distinction. [Pinned Crypt32 wrapper](https://github.com/deploymenttheory/go-bindings-win32/blob/9f51cb95639f/bindings/win32/security/cryptography/cryptography_functions.go#L3359), [pinned callback shape](https://github.com/deploymenttheory/go-bindings-win32/blob/9f51cb95639f/bindings/win32/networking/ldap/ldap_delegates.go#L32).

## Isolated qualification topology and certificate cases

Use the already owned private-switch lab described in [the provisioning note](ad-lab-provisioning.md): no physical-network connection or host trust-store changes. Proposed topology: the member guest hosts an LDS instance `SdkLds` on LDAP `51300` / LDAPS `51301`, partition `CN=SdkLds,DC=lab,DC=test`; a separate owned Windows guest runs the native SDK and reference client. Add an independent no-default instance on `51400` / `51401` if modifying the first instance's default would make cases order-dependent. These are proposed names/ports, subject to the lab's ownership manifest and collision checks.

Provision `ADLDS`, use `ADAMInstall.exe` with a unique instance answer file, import the user schema (`MS-User.LDF`), seed an enabled native-LDS user with a disposable password and read permissions, and record exact endpoint/partition/user DN. Microsoft's first-party setup example supplies the role, answer-file fields, custom ports, partition, service account, and schema import. Its sample credentials are examples, not fixture secrets to reuse. [Microsoft LDS fixture recipe](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/on-premises-ldap-connector-prepare-directory).

For direct LDS TLS, install exactly one eligible certificate in that instance's service Personal store, ensure its private key is readable by the service identity, and trust its issuing root only in the owned server/client guests. Include the actual member FQDN in SAN and Server Authentication EKU. Restart only the owned instance when needed and record the certificate actually presented. Multiple eligible certificates make selection nondeterministic; placing an expired/wrong-name certificate into a store does not prove AD LDS will serve it. [Microsoft LDAPS certificate requirements and AD LDS service-store selection](https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/enable-ldap-over-ssl-3rd-certification-authority).

For certificate generation, `New-SelfSignedCertificate` supports explicit signer, DNS names, usage, and `NotBefore`/`NotAfter`; choose a lab-only root and distinct serial/thumbprint per leaf. A small test-only Go helper can instead generate DER/PEM using `x509.CreateCertificate` with exact SAN and validity fields. For deterministic malformed-peer cases, explicitly select the leaf in a test TLS listener; do not rely on Windows certificate-store ordering. [PowerShell generation](https://learn.microsoft.com/en-us/powershell/module/pki/new-selfsignedcertificate?view=windowsserver2025-ps), [Go certificate generation](https://pkg.go.dev/crypto/x509#CreateCertificate), [Go TLS certificate selection](https://pkg.go.dev/crypto/tls#Config).

| Case | Concrete mechanism and required evidence |
| --- | --- |
| Valid LDAPS and StartTLS | Direct native connections to `51301` and `51300`; actual SIMPLE bind and partition-base/RootDSE reads; record negotiated protocol/cipher and certificate thumbprint. |
| Wrong password | Same valid TLS endpoint and DN, changed nonempty password; retain LDAP invalid-credentials status and prove no retry with current identity. |
| Untrusted issuer | Same server certificate, but a fresh owned client identity/guest without that lab issuer, or a leaf signed by a separate untrusted test root. Never remove unrelated roots. |
| Wrong host | An explicit DNS alias pointing to the same LDS address, omitted from certificate SAN; fresh client process. IP-without-IP-SAN is a separate case. |
| Expired | Generate a correctly named, trusted leaf with `NotAfter` in the past. AD LDS may reject it during selection; a failed listener is not proof of client expiry validation. Use a controlled TLS peer/front end that demonstrably presents that exact leaf. |
| Missing/default partition | Authenticated query for a nonexistent partition; explicit valid partition on no-default instance; omitted partition on no-default instance; never substitute configuration/schema NC. |
| No credentials before TLS | Count bind calls in the native boundary tests; a controlled peer records protocol/application-data events, never secret payloads. Failed/rejected StartTLS and bad-certificate cases must observe zero LDAP BindRequests. |

A deterministic TLS front end can use one configured `tls.Certificate` per listener. For StartTLS, accept only the expected bounded LDAP StartTLS request, return its successful extended response, then perform `tls.Server` on that connection. If successful LDAP forwarding is needed, connect the front end to the real LDS backend using validated LDAPS; a failed outer handshake must never open the credential path. This is a proposed test harness, not an SDK runtime dependency. The old Start-Stop Learn article contains a malformed OID; use the header value. **Qualification blockers:** demonstrate actual presented certificates and fresh connections for each failure case; do not count a server refusing to load an expired certificate as client expiry validation. Keep direct LDS success evidence distinct from controlled-peer TLS rejection evidence. Repeat after the first connection to expose session-cache behavior. Record OS/build/architecture, Wldap32 version, LDS instance ports, relevant policy, certificate thumbprints/validity/SAN, SDK/binding commits, and reference PowerShell/.NET/module versions. Reference clients must use ordinary validation, with no accepting `VerifyServerCertificate` callback. No VM actions or tests were executed for this research note.
