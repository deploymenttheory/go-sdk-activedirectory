# Native WinLDAP connection and RootDSE contracts

Research date: 2026-11-12. Scope: SDK ticket #9, current-identity Negotiate authentication and RootDSE reads, using `go-bindings-win32 v0.6.0`. This note audits API contracts and the pinned source; it is not evidence of successful authentication against the lab. Explicit credential structures belong to ticket #10.

Implementation status: connection work proceeds alongside the remaining lab qualification under #8, as explicitly approved by the user. The memory-ownership correction is tracked by [upstream issue #62](https://github.com/deploymenttheory/go-bindings-win32/issues/62) and [PR #63](https://github.com/deploymenttheory/go-bindings-win32/pull/63). The SDK will consume the corrected upstream binding rather than add its own syscall workaround. Portable configuration validation is implemented; authenticated native RootDSE execution and its qualification remain in progress.

## Binding availability and two upstream hazards

The pinned LDAP package has the build constraint `windows && (amd64 || arm64)`. Its functions use `syscall.SyscallN`; the runtime loader resolves system DLLs lazily from System32. Portable SDK packages must therefore isolate imports of these bindings behind the same build constraint. Construction outside Windows can remain portable, but executing these native calls cannot. [Pinned functions](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_functions.go), [pinned loader](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/runtime/win32/loader.go).

The package exports `ldap.Procs.<Function>`. `Find()` returns a `*win32.ProcError`; `Addr()` panics on resolution failure. `ProcError` preserves the DLL, export and underlying error and supports `ErrDLLNotFound`/`ErrProcNotFound`. Probe every needed export, including cleanup and error-reporting functions, before allocating a session. This permits an actionable unsupported-platform/API error instead of a late panic during cleanup. [Pinned loader, lines 33–166](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/runtime/win32/loader.go#L33), [exported Procs](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_functions.go#L269).

Two generated signatures need particular care:

| Binding | Observed contract and consequence |
| --- | --- |
| `Ldap_bind_sW(ld, dn *string, cred *string, method)` | Both optional strings correctly become NULL when nil. Thus `nil, nil, LDAP_AUTH_NEGOTIATE` supports current identity. A nonnil `cred` becomes a UTF-16 string and cannot represent a `SEC_WINNT_AUTH_IDENTITY[_EX]` pointer. The latter is an upstream signature issue for #10. [Pinned implementation](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_functions.go#L1089). |
| `Ldap_memfreeW(Block string)` | **Unsafe for native allocations:** it allocates a new Go UTF-16 buffer and passes that buffer to the native deallocator. It cannot free the original attribute-name/diagnostic pointer. Never call this wrapper to release a returned native string. An upstream fix must preserve the pointer parameter. The exported `Procs.Ldap_memfreeW` permits a narrowly scoped pointer-preserving call while remaining on the pinned loader. [Pinned implementation](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_functions.go#L1889), [native memory-free contract](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_memfreew). |

`Ldap_memfree` and `Ldap_memfreeA` do preserve their pointer arguments, but this audit has not established a Microsoft guarantee that freeing Unicode allocations through the ANSI export is interchangeable. Calling the matching W export with the original pointer avoids relying on that assumption. The binding's `UTF16Ptr` also panics on embedded NUL; validate public input strings before reaching it. [Pinned functions](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_functions.go#L1875), [pinned string conversion](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/runtime/win32/runtime.go#L90).

## Endpoint, identity and session options

`ldap_initW` allocates a connection block without opening the network connection. A NULL hostname enables default-server discovery; a domain name can also trigger DC discovery. A hostname can contain a port or a space-separated host list, so a public single-endpoint contract must validate those cases. A DNS server hostname should use `LDAP_OPT_AREC_EXCLUSIVE` before connecting to bypass SRV/DC-locator lookup. Every successfully allocated session requires `ldap_unbind`, including connect failure. A nil initialization result requires `LdapGetLastError`. [ldap_initW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_initw).

`ldap_bind_sW` with NULL DN, NULL credentials and `LDAP_AUTH_NEGOTIATE` uses the current user/service credentials. Negotiate selects an available authentication package; it does not guarantee Kerberos. Bind changes the whole connection and must not overlap other operations on that handle. [ldap_bind_sW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bind_sw).

Set signing and encryption before Negotiate bind. These options supply integrity/confidentiality through SASL, and Microsoft documents NTLM support as well as Kerberos. They cannot be combined with SSL. Setting an option successfully is not itself a successful authentication; preserve bind failure rather than retrying with weaker protection. [ldap_set_option](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_set_option), [session options](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/session-options).

| Option | Native value and relevant behavior |
| --- | --- |
| `LDAP_OPT_PROTOCOL_VERSION` | `ULONG(3)`; the documented default is version 2. |
| `LDAP_OPT_SIGN`, `LDAP_OPT_ENCRYPT` | `ULONG(1)` before bind. |
| `LDAP_OPT_AUTO_RECONNECT` | `ULONG(0)` disables implicit reconnection. |
| `LDAP_OPT_REFERRALS` | `ULONG(0)` disables following server referrals. |
| `LDAP_OPT_PROMPT_CREDENTIALS` | `ULONG(0)` prevents credential prompting. |
| `LDAP_OPT_ROOTDSE_CACHE` | `ULONG(0)` disables the normally enabled internal RootDSE cache if fresh reads are required. |
| `LDAP_OPT_SEND_TIMEOUT` | Seconds; bounds sending, returns `LDAP_TIMEOUT`; zero disables this timeout. |

These option meanings and defaults are documented in [session options](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/session-options). Reconnect can involve retry/ping behavior, so its default matters to bounded operations. [Binding to an LDAP server](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/binding-to-an-ldap-server).

The C header defines `LDAP_OPT_ON/OFF` as pointer-valued sentinels `(void*)1` and `(void*)0`; the general setter documentation permits them for Boolean options. This does **not** require constructing invalid Go pointer values. Microsoft's .NET implementation sets signing, sealing and auto-reconnect with an integer variable passed by reference, and its Windows referral setter uses the same path. A pointer to `uint32(1)` or `uint32(0)` follows that demonstrated ABI convention; other integer options also take an address, not the integer reinterpreted as a pointer. [Microsoft header](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/Winldap.h#L805), [.NET option setters/helper](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.cs), [Windows PAL](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/Interop/LdapPal.Windows.cs), [Windows referrals](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.Windows.cs).

## Timeout and cancellation boundaries

| Phase | Documented native bound |
| --- | --- |
| Connect | `ldap_connect` accepts a non-NULL `LDAP_TIMEVAL`; NULL selects a default. An explicit call separates connection errors from authentication errors. [ldap_connect](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_connect). |
| Negotiate bind | `LDAP_OPT_TIMELIMIT` changes the default 120 seconds **per bind-response round trip**. This is not a documented total duration bound on all SSPI/DNS/bind work. [ldap_bind_sW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bind_sw). |
| Send/submission | `LDAP_OPT_SEND_TIMEOUT` addresses a potentially blocked send even for an asynchronous operation. The .NET source explicitly recognizes timeout during async submission as send timeout. [LdapConnection submission](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapConnection.cs#L690). |
| Search | `ldap_search_extW.TimeLimit` specifies seconds for both the local search timeout and the server search limit. Its explicit size/time parameters override `LDAP_OPT_SIZELIMIT/TIMELIMIT`. [ldap_search_extW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_search_extw). |
| Receive | `ldap_result` accepts a finite `LDAP_TIMEVAL`. NULL blocks until results; zero requests polling. [ldap_result](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_result). |

The protocol's ADConnection model independently defines zero `LDAP_OPT_TIMELIMIT` as 120 seconds for binds and unlimited for other requests. The general session-options description emphasizes searches, whereas the bind-specific page explicitly covers bind response waits; do not infer that TIMELIMIT is only server-side. No `LDAP_OPT_NETWORK_TIMEOUT` was found in either the inspected Microsoft header or pinned binding constants; an OpenLDAP option of that name is not a verified WinLDAP contract. [ADConnection model](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/e3681987-53c1-4dd7-930f-15f537046d55), [Microsoft header](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/Winldap.h), [pinned constants](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_constants.go).

Asynchronous `ldap_bindW` supports only `LDAP_AUTH_SIMPLE`; another method produces `LDAP_PARAM_ERROR`. It cannot make current-identity Negotiate cancellable. [ldap_bindW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bindw).

For an asynchronous RootDSE search, the documented primitives support this sequence:

1. Submit `ldap_search_extW`; on success retain its output message ID.
2. Call `ldap_result` with that ID and short finite waits, checking context and Close between waits. `LDAP_MSG_ALL` requests the completed search chain, `LDAP_MSG_ONE` one message, and `LDAP_MSG_RECEIVED` the chain currently received. A return of zero means the wait expired; unsigned `0xffffffff` represents failure. A positive return is a message type, not the server LDAP result code. [ldap_result](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_result).
3. Parse the completed search result's server status, then copy entry data. `ldap_parse_resultW` reports its own parsing status separately from the server status in `ReturnCode`. [ldap_parse_resultW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_parse_resultw).
4. On cancellation, abandon the message ID. Successful `ldap_abandon` destroys the ID, including when already completed; do **not** call `ldap_result` afterward to drain that ID. There is no server acknowledgement, so abandonment does not prove server receipt. Free every message chain already handed to the caller separately. If abandon fails, retain the failure and safely retire the session rather than claiming cancellation completed. [ldap_abandon](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_abandon), [ldap_msgfree](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_msgfree).

Implementation inference: cancellation during connect, synchronous bind, a blocked send or unbind may only be observed after that native call returns. Finite options improve bounds but do not prove a strict aggregate wall-clock deadline. Returning from a detached goroutine on context cancellation does not cancel its native call or transfer permission to free its handle. The audited APIs provide no documented safe interrupt primitive for synchronous Negotiate. Any promise of immediate cancellation in every phase needs additional evidence or a different isolation mechanism.

`ldap_unbind` itself completes synchronously, closes the connection and disposes of the handle without waiting for a server response. Microsoft explicitly warns against calling it twice or using the handle after it is freed. Deterministic Close therefore requires handle ownership coordination: prevent new work, stop/finish owned operations, release their allocations, and unbind exactly once. The documented thread-safety of unbind does not grant permission to continue using freed pointers. [ldap_unbind](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_unbind).

## RootDSE projection and capability facts

The RootDSE read is a base-scope search at the empty DN with `(objectClass=*)` and attribute values enabled. Microsoft's protocol examples use that exact shape. [MS-WKST RootDSE search](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wkst/0d84af25-9310-4b2e-bcba-b9b085554102).

`ldap_search_extW` accepts a NULL-terminated array of NULL-terminated attribute names, with NULL requesting all available attributes and `attrsonly=0` requesting values. The binding distinguishes `base=nil` from a pointer to `""`; use the latter for the explicit empty RootDSE DN. [ldap_search_extW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_search_extw), [pinned wrapper](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_functions.go#L2465).

At the protocol level, empty attribute selection or `*` asks for user attributes; `*` can be combined with explicitly named operational attributes. Access restrictions may still omit attributes. Hence “all attributes” must not promise every operational RootDSE property. [RFC 4511 section 4.5.1.8](https://www.rfc-editor.org/rfc/rfc4511.html#section-4.5.1.8).

RFC 3673 defines `+` for operational attributes, but allows omissions and attributes requiring explicit names; unsupported servers ignore it. Blanket support across AD versions was not established in this audit. Microsoft marks RootDSE operational attributes as explicitly requested only. Default, selected and all modes are SDK projection choices: a stable default list; that list plus selected names if the SDK promises additive selection; and `*` plus explicit requested names for the documented available/user-attribute behavior. [RFC 3673](https://www.rfc-editor.org/rfc/rfc3673.html), [MS-ADTS RootDSE attributes](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/96f7b086-1ca3-4764-9a08-33f8f7a543db).

RootDSE properties support typed views while raw values remain necessary:

| Property group | Published syntax/meaning |
| --- | --- |
| Naming contexts, `serverName`, `dsServiceName`, `subschemaSubentry` | Distinguished names. |
| `currentTime` | Generalized Time. |
| `highestCommittedUSN` | LargeInteger. |
| `isSynchronized`, `isGlobalCatalogReady` | Boolean. |
| Functional levels, `supportedLDAPVersion` | Integer. |
| `supportedCapabilities`, `supportedControl` | Object identifiers; retain unknown identifiers. |
| `supportedSASLMechanisms`, `supportedLDAPPolicies`, `dnsHostName` | Strings. |

These syntaxes and version-dependent attribute availability are listed in [MS-ADTS RootDSE attributes](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/96f7b086-1ca3-4764-9a08-33f8f7a543db). Capability/control/version collections describe server support; they are not proof that a particular feature or authentication mechanism was negotiated for this session. Multivalued naming contexts and capability lists should not be reduced to their first value. [RootDSE schema reference](https://learn.microsoft.com/en-us/windows/win32/adschema/rootdse).

## Native ownership and nullability audit

| Native object/result | Ownership and required action |
| --- | --- |
| `LDAP*` from init | Owned, nullable on failure; exactly one unbind on every successful allocation path, including failed configuration/connect/bind. [ldap_initW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_initw). |
| `LDAPMessage*` from result | Owned chain. Free with `ldap_msgfree`, including partial chains returned on an error/cancellation path. Entry pointers returned from entry traversal refer to the chain; do not free them individually. [ldap_msgfree](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_msgfree), [ldap_first_entry](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_first_entry). |
| Attribute name from first/next attribute | Owned native UTF-16 string. Copy and free the original pointer before advancing. NULL means enumeration end only if the LDAP session status is success; otherwise it is an error. [ldap_first_attributeW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_first_attributew). |
| `BerElement*` enumeration cursor | `ldap_first_attributeW` allocates it. Free nonnil cursor with `ber_free(cursor, 0)` on success, error and early exit. It does not own the message buffer. [ldap_first_attributeW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_first_attributew). |
| `berval**` from `ldap_get_values_lenW` | Owned NULL-terminated pointer array; free exactly once with `ldap_value_free_len`. NULL with success means no values; NULL with a session error means failure. [ldap_get_values_lenW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_get_values_lenw). |
| Each `berval` payload | Borrowed from the value array. Copy exactly `bv_len` bytes before freeing it; length is bytes and content is arbitrary binary, not NUL-terminated UTF-16. Preserve zero-length values. Validate a nonzero length with a nil pointer before constructing an unsafe slice. [LDAP_BERVAL](https://learn.microsoft.com/en-us/windows/win32/api/winldap/ns-winldap-ldap_berval). |
| Parse-result outputs | Optional output arguments may be nil. Requested `MatchedDNs` and `ErrorMessage` are owned strings freed through the matching native memfree; referrals require `ldap_value_free`, controls `ldap_controls_free`. Use `Freeit=0` when a separate owner frees the result chain. [ldap_parse_resultW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_parse_resultw). |
| `ldap_err2stringW` text | Borrowed static string, possibly nil; copy as needed, never free. [ldap_err2stringW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_err2stringw). |

The pinned `LDAP_TIMEVAL` contains two `int32` fields; `LDAP_BERVAL` contains a `uint32` length and pointer. Duration conversion must avoid integer overflow, normalize microseconds, and avoid rounding a positive finite limit down to zero where zero means unlimited. UTF-16 names and raw attribute value bytes are different representations. [Pinned structs](https://github.com/deploymenttheory/go-bindings-win32/blob/v0.6.0/bindings/win32/networking/ldap/ldap_structs.go#L164).

## Go pointer lifetime and error domains

The generated wrappers convert pointers directly inside `syscall.SyscallN` argument expressions. This is Go's documented special case for retaining passed allocations through the native call. A stored `uintptr` is not a GC reference. Own attribute-name buffers and their pointer-array storage through search submission, with typed references and an explicit `runtime.KeepAlive` boundary where needed. KeepAlive does not establish permission for native code to retain pointers after return. [Go unsafe rules](https://pkg.go.dev/unsafe#Pointer), [Go runtime](https://pkg.go.dev/runtime#KeepAlive).

Microsoft's API page marks search inputs as `[in]` but does not expressly document every buffer-retention detail. Strong implementation evidence exists: .NET marshals attribute strings/array, submits asynchronous `ldap_search_extW`, and frees these buffers in the submission method's `finally`, before result retrieval. This supports call-scoped search input lifetime; it is evidence from Microsoft's client implementation rather than a new explicit WinLDAP specification guarantee. [LdapConnection source, submission and cleanup](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapConnection.cs#L642), [Windows mapping to WinLDAP](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/Interop/LdapPal.Windows.cs#L65).

No retained callback or alternate-credential structure is needed for this current-identity path. If future code gives native code retained Go pointers, `runtime.Pinner` prevents movement/freeing; reachable objects must be pinned separately where accessed from native code. This does not fix an incorrect ownership contract. [Go Pinner](https://pkg.go.dev/runtime#Pinner).

Preserve the LDAP numeric result returned by option/connect/bind/search functions. Do not interpret it as a Win32 `GetLastError` code. On APIs whose failure is NULL or unsigned -1, collect the documented LDAP status immediately. `LdapGetLastError` is **OS-thread-local**: lock the goroutine to its OS thread across the failing native call and that getter, or obtain the documented session error where a valid handle exists. [LdapGetLastError](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldapgetlasterror), [Go LockOSThread](https://pkg.go.dev/runtime#LockOSThread).

`LDAP_OPT_ERROR_NUMBER` is the session's LDAP status. `LDAP_OPT_ERROR_STRING` is borrowed text that the caller must not free. `LDAP_OPT_SERVER_EXT_ERROR` belongs to the Win32 server-error domain. Keep these domains distinct. [Session options](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/session-options). For `LDAP_OPT_SERVER_ERROR`, the documentation does not state ownership explicitly; .NET retrieves it using its freeing helper, unlike borrowed `LDAP_OPT_ERROR_STRING`. This is implementation evidence, and the pointer-preserving memfree limitation still applies. [.NET Windows diagnostic getter](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.Windows.cs#L50), [.NET string option helper](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.cs#L745).

Capture status and diagnostic copies before subsequent cleanup or other operations overwrite native state. A result parser's success does not replace a failed server `ReturnCode`; a cleanup error does not replace the original operation error. Context errors can be reported alongside preserved native failure information. These are consequences of the distinct return/output contracts above, rather than additional WinLDAP guarantees.
