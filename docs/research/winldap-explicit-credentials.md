# Explicit WinLDAP Negotiate credential contracts

Research date: 2026-11-12. Scope: SDK ticket #10, explicit username/domain/password authentication while preserving current-identity authentication. Sources are Microsoft's API documentation, Windows SDK headers, .NET runtime source, Go source/documentation, and the SDK's pinned `go-bindings-win32 v0.6.1-0.20261112122428-33694fcc8fb1`. This is a contract/source audit, not a successful lab authentication result. It supplements [the connection audit](winldap-connection.md).

Recommendation: use one private owner for the identity structure and its mutable UTF-16 buffers during synchronous bind. Release that owner after bind returns, with native password zeroing before unpinning. Do not retain the public credentials in `Client` or `ldapSession`. The lifetime recommendation relies on the first-party implementation evidence below; Microsoft's WinLDAP reference does not explicitly promise that it never retains the caller's pointers.

## Method-dependent pointer and UTF-16 representation

For `LDAP_AUTH_NEGOTIATE`, set `dn` to NULL. A NULL `cred` selects the current user/service credentials; an explicit identity uses a pointer to `SEC_WINNT_AUTH_IDENTITY` or `_EX`. The superficially string-shaped `cred` parameter must therefore preserve the structure's address. Negotiate selects an authentication package and does not guarantee Kerberos. Bind affects the entire connection and must not overlap other operations. [Microsoft: ldap_bind_sW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bind_sw).

The audited pin still converts `cred *string` to UTF-16, so it cannot pass an identity structure. The proposed upstream `foundation.PWSTR` correction is a prerequisite; it must pass the address unchanged rather than dereferencing it as text. Reuse the generated `rpc.SEC_WINNT_AUTH_IDENTITY_W`, whose pointers are `*uint16`, lengths are `uint32`, and flags use `rpc.SEC_WINNT_AUTH_IDENTITY`. Its package location does not change which Windows APIs may consume it. [Pinned LDAP wrapper](https://github.com/deploymenttheory/go-bindings-win32/blob/33694fcc8fb1/bindings/win32/networking/ldap/ldap_functions.go#L1089), [pinned identity structure](https://github.com/deploymenttheory/go-bindings-win32/blob/33694fcc8fb1/bindings/win32/system/rpc/rpc_structs.go#L1419).

Set `Flags` to `SEC_WINNT_AUTH_IDENTITY_UNICODE`. Each length counts UTF-16 code units, excluding an optional terminating zero: `len(encoded)-1` for a terminated buffer, not Go UTF-8 byte length or rune count. For example, one supplementary Unicode character occupies two units. The identity reference specifies character lengths excluding terminators; .NET supplies its UTF-16 `string.Length`, corroborating the unit. Check length representability before narrowing to `uint32`. [Microsoft: identity fields](https://learn.microsoft.com/en-us/windows/win32/api/sspi/ns-sspi-sec_winnt_auth_identity_w), [.NET BindHelper](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapConnection.cs#L963), [Go UTF-16 encoding](https://go.dev/src/unicode/utf16/utf16.go).

SDK policy should reject embedded NUL and invalid UTF-8 in every credential field before native conversion. `utf8.ValidString` validates scalar UTF-8; Go's Windows `UTF16FromString` rejects embedded NUL but deliberately supports WTF-8 for unpaired surrogates, so it does not replace that validation. Do not trim, case-fold, or normalize passwords. Allocate the final buffer once; iterating the validated string directly into a pre-sized UTF-16 buffer avoids an intermediate `[]rune` password copy and append reallocations. These are SDK input/ownership choices, not claims that SSPI requires every such rejection. [Go UTF-8 validation](https://pkg.go.dev/unicode/utf8#ValidString), [Go 1.25 Windows conversion](https://github.com/golang/go/blob/go1.25.0/src/syscall/syscall_windows.go#L36).

Microsoft's Negotiate credential-acquisition page also lists username/password/domain maxima of 256/256/15 characters. These are package-level documentation, not the identity structure's integer capacity or a complete WinLDAP name-validation contract. Do not silently truncate fields or infer a universal DNS-domain limit from that page; let native authentication report unsupported account forms unless the SDK deliberately documents narrower input rules. [Microsoft: AcquireCredentialsHandle (Negotiate)](https://learn.microsoft.com/en-us/windows/win32/secauthn/acquirecredentialshandle--negotiate).

## Presence, empty values, and account names

| Input case | Recommended SDK mapping |
| --- | --- |
| Credentials absent | `dn=nil`, `cred=nil`; preserve the existing current-identity path. |
| Credentials present | Non-NULL identity pointer; validate the explicit username is nonempty. Never convert an empty credential object to current identity. |
| Domain omitted | `Domain=nil`, `DomainLength=0`; document that this means unspecified domain. |
| Domain supplied | Preserve its text in its own UTF-16 buffer and set the corresponding length. |
| Empty explicit password, if supported | Use an allocated zero-terminated empty buffer with a non-NULL `Password` pointer and length zero. Keep `cred` non-NULL. Alternatively reject it explicitly as SDK policy. |

The NULL-credential rule is documented for the whole `cred` argument. The inspected WinLDAP and identity pages do **not** fully specify whether NULL and non-NULL zero-length individual fields are equivalent across Negotiate providers. Do not extend the whole-pointer rule into a guarantee about a NULL password or cached credentials. In particular, an explicit failure must never trigger a second bind with NULL credentials. [Microsoft: ldap_bind_sW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bind_sw), [Microsoft: identity fields](https://learn.microsoft.com/en-us/windows/win32/api/sspi/ns-sspi-sec_winnt_auth_identity_w).

.NET intentionally maps an all-empty `NetworkCredential` to default credentials, then passes username/domain/password independently without parsing or splitting their text. This is evidence about .NET behavior, not a policy the SDK should inherit. Its non-default empty strings remain empty strings in the marshaller. [.NET BindHelper](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapConnection.cs#L929), [.NET credential marshaller](https://github.com/dotnet/runtime/blob/main/src/libraries/Common/src/Interop/Interop.Ldap.cs#L34).

Recommended documented forms are an account name with a separate domain, or the complete UPN in `User` with omitted domain. Preserve a UPN intact: its suffix can be explicitly configured and need not be the account's DNS domain. Microsoft's `LogonUserW` explicitly requires NULL domain for a UPN, but that is a different API; it is supporting evidence for this representation, not proof of every WinLDAP/SSPI case. The inspected WinLDAP page's UPN language describes `dn`, while Negotiate requires `dn=NULL`, so it cannot independently prove UPN handling inside `User`. Qualify the UPN form against the lab before claiming support. Avoid guessing a domain from the endpoint, rewriting `DOMAIN\user`, or discarding a supplied domain when a UPN is present; either preserve explicit fields or reject ambiguous combinations under documented SDK rules. [Microsoft: user-name formats](https://learn.microsoft.com/en-us/windows/win32/secauthn/user-name-formats), [Microsoft: LogonUserW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-logonuserw).

## Lifetime: contract gap and first-party evidence

The `SEC_WINNT_AUTH_IDENTITY_W` lifetime warning in `sspi.h` documentation explicitly concerns **RPC** binding handles. The generated type living in the Go `rpc` package does not make the LDAP handle an RPC handle. This warning cannot justify retaining plaintext for the whole LDAP session. The WinLDAP bind page describes synchronous execution but gives no explicit input-buffer retention/copy contract. [Microsoft: identity remarks](https://learn.microsoft.com/en-us/windows/win32/api/sspi/ns-sspi-sec_winnt_auth_identity_w), [Microsoft: ldap_bind_sW](https://learn.microsoft.com/en-us/windows/win32/api/winldap/nf-winldap-ldap_bind_sw).

Microsoft's .NET Windows implementation supplies more concrete evidence:

1. `BindHelper` constructs a local `SEC_WINNT_AUTH_IDENTITY_EX`; `InternalBind` passes it to the Windows interop layer. [.NET Windows connection](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapConnection.Windows.cs#L59).
2. The Windows import calls `ldap_bind_sW` with `in SEC_WINNT_AUTH_IDENTITY_EX`. [.NET Windows P/Invoke](https://github.com/dotnet/runtime/blob/main/src/libraries/Common/src/Interop/Windows/Wldap32/Interop.Ldap.cs#L12).
3. Its custom input marshaller allocates native user/domain/password strings using `StringToCoTaskMemUni`, then frees each with `FreeCoTaskMem` in the marshaller's cleanup. These native allocations are scoped to the invocation, not the LDAP session. [.NET credential marshaller](https://github.com/dotnet/runtime/blob/main/src/libraries/Common/src/Interop/Interop.Ldap.cs#L48), [Microsoft: custom marshaller cleanup](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/custom-marshaller-shapes).

**Inference:** releasing caller-owned buffers after synchronous return matches Microsoft's maintained .NET implementation. This is strong implementation evidence, not an express WinLDAP guarantee that all credential information disappears. .NET retains a separate managed `NetworkCredential` for its own subsequent binding behavior; retaining that managed object cannot keep the already-freed marshalling buffers valid. [.NET credential storage and bind entry points](https://github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapConnection.cs#L897).

WinLDAP can automatically reconnect; the AD protocol model also records authentication information on the connection. Neither fact proves retention of the original caller pointers rather than native copies/security handles. Keep automatic reconnect and referral chasing disabled as in ticket #9. Do not advertise that these options prevent all Windows credential caching or that zeroing SDK memory erases Windows-owned authentication state. [Microsoft: reconnect behavior](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/binding-to-an-ldap-server), [MS-ADTS connection model](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/e3681987-53c1-4dd7-930f-15f537046d55).

## Go ownership and wiping without new raw syscalls

Pin the identity object and each nonnil backing array for the native calls; pinning an object does not recursively pin objects referenced by its fields. Keep the owner reachable through bind and cleanup, and unpin deterministically afterward. This makes the nested-pointer boundary explicit without relying on Go's current nonmoving heap. `runtime.KeepAlive` is not a substitute for pinning or valid unsafe conversions. Keep addresses as typed pointers; do not retain them in intermediate `uintptr` variables. [Go 1.25 Pinner contract](https://github.com/golang/go/blob/go1.25.0/src/runtime/pinner.go#L18), [Go KeepAlive](https://pkg.go.dev/runtime#KeepAlive), [Go unsafe syscall rules](https://pkg.go.dev/unsafe#Pointer).

An existing native wipe is available: `identity.SspiZeroAuthIdentity(unsafe.Pointer(&auth))`. Microsoft's header shows that the opaque identity representation includes the ordinary `SEC_WINNT_AUTH_IDENTITY_W`; the zeroing API accepts that representation. This supports using the typed binding on the manually built, pinned identity after bind has returned. Keep buffers pinned until the wipe returns. Probe this export before allocating explicit credentials so cleanup cannot fail with a late loader panic. The function is `VOID` in both header and binding; the Learn page's success/error return prose is inconsistent with its signature. [Microsoft: SspiZeroAuthIdentity](https://learn.microsoft.com/en-us/windows/win32/api/sspi/nf-sspi-sspizeroauthidentity), [Microsoft SDK identity union](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/sspi.h#L2787), [pinned typed wrapper](https://github.com/deploymenttheory/go-bindings-win32/blob/33694fcc8fb1/bindings/win32/security/authentication/identity/identity_functions.go#L2572).

After the native wipe, clear all SDK-owned UTF-16 slices and reset the identity fields, then unpin. Do not depend on `SspiZeroAuthIdentity` to erase usernames, domains, structure padding, or copies outside that identity. Go `clear` zeroes slice elements, but its language contract is not a promise of cryptographic secure erasure of every copy; `KeepAlive` adds no such promise. Microsoft documents `SecureZeroMemory` specifically to avoid dead-store elimination, but it is defined inline as `RtlSecureZeroMemory`, and this audit found no corresponding wrapper in the pinned bindings. [Go clear semantics](https://go.dev/ref/spec#Clear), [Microsoft: SecureZeroMemory](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/aa366877(v=vs.85)).

Do **not** call `SspiFreeAuthIdentity` on Go memory. It belongs to native allocation ownership. The SDK header directs results from `SspiCopyAuthIdentity` and `SspiEncodeStringsAsAuthIdentity` to that free function and states that it zeroes credentials before freeing. Encoding/copying is unnecessary for this simple bind owner: the pinned encoder accepts `*string` and creates additional hidden UTF-16 buffers, and its documentation describes packed credentials rather than promising that all input is an ordinary password. Avoid expanding the feature into opaque credential storage solely to obtain a wipe. [Microsoft SDK allocation/cleanup comments](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/sspi.h#L3250), [Microsoft: encoder](https://learn.microsoft.com/en-us/windows/win32/api/sspi/nf-sspi-sspiencodestringsasauthidentity), [pinned encoder/free wrappers](https://github.com/deploymenttheory/go-bindings-win32/blob/33694fcc8fb1/bindings/win32/security/authentication/identity/identity_functions.go#L2431).

The defensible public claim is limited: the SDK clears its temporary native-call password buffer after bind returns and does not intentionally retain credentials in the client. Go strings are immutable, and the caller, conversions, runtime, or Windows may retain other copies. Never claim complete password erasure. [Go string semantics](https://go.dev/ref/spec#String_types).

## Smallest implementation boundary and verification

The implementation recommendation is a private bind helper that owns conversion, pinning, the native call, zeroing, and unpinning. Current identity uses the existing NULL path without constructing an identity. Explicit credentials belong only to `Dial` and its synchronous bind helper; do not add a persistent credential store, background authentication goroutine, reconnect mechanism, or extra SSPI credential handle. On every bind result, cleanup occurs after the native call returns. On failure/cancellation, preserve the existing session-unbind path. This is the SDK design conclusion drawn from the lifetime and ownership evidence above.

Preserve numeric LDAP errors and fixed operation names. Validation errors should identify the invalid field without including its value; never format a credential struct, password buffer, or configuration containing credentials into logs or errors. A formatter/redactor can reduce accidental exposure but cannot make exported password fields impossible for callers to print. This is an SDK confidentiality requirement, not a guarantee supplied by the WinLDAP API.

Focused checks should cover NULL versus explicit identity, separate domain and UPN representations, supplementary characters and exact lengths, rejected NUL/invalid UTF-8, no fallback after invalid credentials, cleanup after bind success/failure/cancellation, and a post-bind RootDSE read after buffers have been cleared. Test native wiping with synthetic data on Windows, including that it does not free Go-owned storage; qualify successful explicit authentication and a deliberately wrong password in the lab. Those observations validate the chosen implementation but must not be presented as proof that undocumented lifetime behavior holds on every Windows version.
