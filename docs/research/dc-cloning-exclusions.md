## What the operation actually does

The documented inventory is SCM services and machine-wide installed programs under `HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall`. The excluded result is the inventory remaining after the system default and selected custom inclusion list. This is not LDAP search, an ADWS operation, MSI-only enumeration, or a remote target operation. [Microsoft's inventory description](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh831734%28v%3Dws.11%29).

The reference DC returned 28 `Microsoft.ActiveDirectory.Management.Commands.ADDCCloningExcludedApplication` objects, each exposing `Name` and `Type` strings. All 28 had type `Service`. Its 133 service names, compared case-insensitively with the 156 service entries in its default XML, produced exactly those 28 names. Exact-case comparison incorrectly adds `EapHost`, `mpssvc`, and `SNMPTrap`. The excluded set contains two disabled services, eighteen manual services, and eight automatic services: filtering to running or enabled services is incorrect for this observed build. Both registry views contained a `WIC` subkey without `DisplayName`; neither became an exclusion. These observations do not establish program-name, Unicode comparison, wildcard, or version semantics. [Captured inventory and output](dc-cloning-evidence/server2025-readonly.json).

The cmdlet documents that applications must be evaluated by their vendors before inclusion. An inclusion record is an administrator's assertion, not a proof that software is safe to clone. The SDK should therefore expose exclusions and generated artifacts, not a `SafeToClone` verdict. [Cmdlet workflow](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-addccloningexcludedapplicationlist?view=windowsserver2025-ps).

## Actual exports and why not to guess their ABI

Read-only inspection of the installed Microsoft AD assembly identified these P/Invoke declarations in `Microsoft.ActiveDirectory.Management.UnsafeNativeMethods`; the [Server 2025 probe](dc-cloning-evidence/server2025-contracts-readonly.json) independently confirms the parameter names and marshaling:

| Export in `dsrolesrv.dll` | Observed managed declaration and marshaling |
| --- | --- |
| `DsRoleIsPassedAllowedList` | Returns `Int32`; arguments are input `Boolean fUseCustomerAllowList` (`UnmanagedType.Bool`), output `Boolean pfIsAllowed` (`Bool`), output string `pbstrFailedList` (`BStr`), output string `ppwszCustomerAllowListFileName` (`LPWStr`), output `Int32 piCustomAllowListFileNameRank` (`I4`). |
| `DsRoleGetCustomAllowListPathRank` | Returns `Int32`; input string `pwszCustomerAllowPath` (`LPWStr`), output `Int32 piCustomAllowListPathRank` (`I4`), output string `ppwszHighestRankedPath` (`LPWStr`), output `Int32 piHighestRankedPathRank` (`I4`). |

Both declarations use `CharSet.Auto`, `CallingConvention.Winapi`, `PreserveSig=true`, and `SetLastError=false`. This records what Microsoft's caller does; it does **not** prove allocation/deallocation rules for an independent Go caller, behavior on failure, support across releases, or native ARM64 availability. Searches of Microsoft Learn, the local Windows SDK `10.0.19041.0` headers, and the pinned generated bindings found no public declarations for these names. Do not invent a `DsRoleGetDCCloningExcludedApplicationList` API or use `DsAddCloneDCW`: finding a similarly named export does not establish an inventory contract.

On the reference DC, `dsrolesrv.dll` is file version `10.0.26100.1`, SHA-256 `6AA3E5CCB7157DFDE373440CE7F61180F2AFCB8F6BAA51B931DFDB3ACA66B03E`. `GetProcAddress` confirms both exports and `DsRolepCheckExistingCloneConfigFile` exist. No export was invoked. The third export concerns clone configuration and is outside this ticket's inventory/list generation. [Native-contract observation](dc-cloning-evidence/server2025-contracts-readonly.json).

The development host's `dsrole.dll` export table contains only `DsRoleFreeMemory` and `DsRoleGetPrimaryDomainInformation`. This is distinct from `dsrolesrv.dll`, which was not installed there. Export existence on a DC is useful evidence but is not, by itself, a supported interface contract. If a public owner contract is later located, any new wrapper and allocation fixes belong in the upstream generator, with regenerated bindings and ownership tests; never add a handwritten syscall substitute in this SDK. [Upstream contribution rules](https://github.com/deploymenttheory/go-bindings-win32/blob/main/CONTRIBUTING.md).

## List discovery and exact XML shape

Read the default from the actual system directory, `DefaultDCCloneAllowList.xml`; do not distribute a hard-coded list or modify the system file. Microsoft identifies its location as `%windir%\system32` and warns against moving/editing it. [Default list contract](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh831734%28v%3Dws.11%29).

Microsoft documents this custom-list order, with only the first existing file used:

1. Folder in `HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters\AllowListFolder` (`REG_SZ`).
2. DSA Working Directory.
3. `%windir%\NTDS`.
4. Root of removable read/write media, ordered by drive letter.

The filename is `CustomDCCloneAllowList.xml`. A malformed higher-priority file is not permission to merge or fall back to a lower-priority file; Microsoft documents syntax failure separately. Distinguish missing candidates from access or parsing failure. [Search order and first-file rule, event 29250; syntax failure, event 29267](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/virtual-dc/virtualized-domain-controller-troubleshooting).

On the observed DC, `AllowListFolder` was absent and `DSA Working Directory` was `C:\Windows\NTDS`. No custom file was captured. The default XML was 14,508 bytes, SHA-256 `F0765D1E7BF71C9A86C19D64EF1D27193A20846CACE585452BA5D89F08E605F5`. Its root is unqualified `DefaultCloneConfig`, containing `AllowList/Allow` records and a separate `sysprepInformation` subtree. Only the allow-list subtree belongs to inventory comparison; the SDK must neither execute nor rewrite sysprep data. [Captured default file](dc-cloning-evidence/server2025-readonly.json).

The DC ships the exact custom schema as `%windir%\System32\CustomDCCloneAllowListSchema.xsd`, 744 bytes, SHA-256 `DB65EC459C4966A724C0E73751F65D120AA19D42D761673952D6791897B590C5`. Its contract is:

| Item | Schema rule |
| --- | --- |
| Root | Local name `CustomDCCloneAllowList`, namespace `uri:microsoft.com:schemas:CustomDCCloneAllowList`. |
| Children | `Allow`, unqualified namespace, one or more, unbounded maximum. |
| Entry fields | Exactly one unqualified `Name` and one unqualified `Type`; `xs:all` permits either order. |
| Value types | Both `xs:string`; no enum, version field, length restriction, or uniqueness constraint. |
| Unknown fields | No wildcard extension is declared. A `Version` element is not part of this captured schema. |

Consequences: an empty custom root is not schema-valid, duplicate `Allow` entries are not prohibited by XSD, and a wrong/unknown type string can be schema-valid yet semantically invalid. Do not conflate schema validation with the native consumer's matching behavior. Do not accept the internal `<AllowList>` result root as the custom file's root, or confuse this XSD with `DCCloneConfigSchema.xsd`. [Captured Microsoft XSD](dc-cloning-evidence/server2025-readonly.json).

A schema-conforming generated record has this shape; the example name is deliberately synthetic:

```xml
<?xml version="1.0" encoding="utf-8"?>
<dc:CustomDCCloneAllowList xmlns:dc="uri:microsoft.com:schemas:CustomDCCloneAllowList">
  <Allow>
    <Name>ExampleService</Name>
    <Type>Service</Type>
  </Allow>
</dc:CustomDCCloneAllowList>
```

Use an XML encoder for values. A default namespace on the root would also qualify unprefixed children unless explicitly reset, and therefore would change this schema. A Go `encoding/xml` decoder does not enforce XSD by itself: validate root namespace, allowed children, field cardinality, and trailing content explicitly. UTF-16 input, BOM handling, and native parser permissiveness remain differential cases; encode generated files as UTF-8 without a BOM, following the observed cmdlet writer. These are implementation decisions grounded in the captured schema and the local binary observations below.

## Generation differs from ordinary discovery

Read-only IL inspection of `GetADDCCloningExcludedApplicationListBaseProcessCSRoutine` in the identified local assembly establishes this behavior for file version `10.0.26100.7920`:

1. It probes whether `dsrolesrv.dll` loads. Failure produces a local-machine-not-DC warning and no result. This is implementation evidence, not a sufficient SDK role test.
2. In generation mode it resolves `Path` to a full directory path and calls `DsRoleGetCustomAllowListPathRank`. A negative output rank is rejected. If no path was supplied, it uses the returned highest-ranked path. Which directories the helper accepts is still a live-probe question.
3. It calls `DsRoleIsPassedAllowedList` with `fUseCustomerAllowList = !GenerateXml`. IL at offset `0x019c` is `ldloc.s 6; ldc.i4.0; ceq`, where local 6 is the GenerateXml Boolean. Thus generation recomputes the inventory against the **default list only**; it does not write the default+custom delta.
4. A nonzero native return is interpreted through `Win32Exception`. If the native `pfIsAllowed` result is true, the routine returns without writing a file, even in generation mode.
5. In discovery mode, it parses the native XML and enumerates `Allow` elements. Each record becomes an `ADDCCloningExcludedApplication` with `Name` and `Type`. The managed record adapter compares those field names ordinally ignoring case; that does not establish how native input XML is matched.
6. In generation mode, a lower-priority destination than the existing custom location is rejected, including with Force. Equal-rank existing output is rejected unless Force is set. Do not reduce Force to bypassing all precedence checks.
7. It removes the native `<AllowList>` container, wraps its children in the namespaced custom root shown above, and writes `CustomDCCloneAllowList.xml` with `UTF8Encoding(false)` and an indented `XmlTextWriter`.

These facts must be rechecked against the lab's different assembly build and each supported server generation. Exact whitespace, newline style, record ordering, arbitrary-path acceptance, existing-empty-file behavior, and the helper's numeric rank convention are not established merely by knowing the wrapper. Keep semantic XML equivalence and byte-format evidence separate.

The pinned SCM wrappers already accept nullable names and a byte buffer; registry wrappers return `WIN32_ERROR` directly. The old role wrapper used `string`, which could not represent documented NULL. ## Host prerequisites and API design

Keep this capability independent of the network `Client`: proposed package `dccloning` with local `Inspect(ctx)` and `Generate(ctx, GenerateOptions{Directory, Overwrite})`. No server argument, LDAP credentials, PowerShell subprocess, RSAT runtime dependency, WMI agent, or remote execution. This is a design recommendation from the ticket's local-operation scope, not an existing public API.

Return typed entries containing original `Name`, kind, inventory source/view, and diagnostic provenance. Start with observed `Service`; reserve typed `Program`/`WoW64Program` classification only after positive reference fixtures establish those tokens and their matching rules. Preserve unknown input type strings in diagnostics instead of silently mapping them to services. Include the chosen default/custom paths, source file identities, role, inventory scope, and issues in the result. A non-nil error can accompany valid partial entries. Keep native status codes available through a typed error and `Unwrap`, separately from parse, unsupported-feature, and validation errors.

The documented use is a local AD DS domain controller. Validate Windows/architecture/export availability and local DC role before inventory or writes; AD LDS-only, member-server, and workstation hosts are prerequisite failures for this operation. Do not reject RODCs merely because they are read-only: Microsoft explicitly says writable and read-only DCs support virtualized-DC capabilities. VM-Generation ID, PDC availability, and clone permission are cloning prerequisites, not proved prerequisites for this read-only inventory call. Record them separately if later exposed; do not contact the domain or enforce them by inference. [Deployment requirements](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/virtual-dc/virtualized-domain-controller-deployment-and-configuration), [vendor test guidance](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/reference/virtual-dc/virtualized-domain-controller-cloning-test-guidance-for-application-vendors).

Generation should require an explicit directory in the Go API, return the exact resulting file path and outcome, and write only that directory's `CustomDCCloneAllowList.xml`. Resolve discovery and ranking before writes. Preserve the existing file until a complete encoded result is ready. Use a same-directory temporary file plus a tested publication primitive with explicit no-overwrite/overwrite behavior; clean up only that temporary file. Refuse generation on incomplete inventory or invalid selected lists. If publication fails after it might have occurred, return an uncertain-write result and do not automatically retry. An empty default-only exclusion set should produce a no-file outcome, matching the observed wrapper. These are proposed safety/ownership semantics; prove observable parity with reference tests.
