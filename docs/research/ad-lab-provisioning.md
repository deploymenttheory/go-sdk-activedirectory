# Reproducible Hyper-V Active Directory lab

Research date: 2026-11-11. Sources are Microsoft product documentation, API documentation, protocol specifications, and the Microsoft Directory Services team. This is a provisioning design note, not a report that the lab has been deployed or validated.

## Initial profile and isolation

The initial requested profile is three Windows Server 2025 guests: two writable domain controllers and one domain member, with artifacts under `H:\ad-sdk-lab`. The ISO inspection supplied for this work identifies image 1 as Standard Evaluation Server Core and image 2 as Standard Evaluation Desktop Experience. Those indices are observations about that ISO, not a portable mapping for other ISOs. Record ISO SHA-256, image index/name, architecture, image version and installed guest build with each run.

Use a dedicated `Private` Hyper-V switch. Private switches connect guests on the same host without connecting the host or physical network; `Internal` also connects the host, and `External` connects a physical adapter. The switch creation contract is `New-VMSwitch -Name <owned-name> -SwitchType Private`; supplying `-NetAdapterName` or `-NetAdapterInterfaceDescription` instead selects an external switch. [Hyper-V networking](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/plan/plan-hyper-v-networking-in-windows-server), [New-VMSwitch](https://learn.microsoft.com/en-us/powershell/module/hyper-v/new-vmswitch?view=windowsserver2025-ps).

Design decisions for this lab: one adapter per guest; static addresses within one private subnet; no guest default gateway, NAT, Internet Connection Sharing, physical adapter binding, or change to existing switches. Domain members use lab DC DNS addresses. Manage and transfer artifacts through PowerShell Direct. Record VM IDs, disk paths and switch IDs in an ownership manifest; refuse name collisions or an existing switch of a different type. Do not reuse or reconfigure existing VMs merely because their names resemble the lab prefix.

Evaluation media imposes a duration constraint: Microsoft says Server 2025 Evaluation expires after 180 days and requires Internet activation within the first 10 days to avoid automatic shutdown. An indefinitely usable, completely disconnected evaluation lab therefore needs a separately resolved licensing/activation plan. Preserve the requested isolation; do not silently attach a public network to activate. [Microsoft Evaluation Center](https://www.microsoft.com/en-gb/evalcenter/evaluate-windows-server-2025).

## Offline image application and first boot

1. Create a **new** VHDX, mount only that exact path, and derive its disk object from `Mount-VHD -PassThru | Get-Disk`. Microsoft documents this mapping. As a lab guard, require that the resolved VHDX path is below the owned root and that the disk is not the host boot/system disk. Never adapt a sample that initializes every RAW disk, and never assume the new disk is disk 0. [Mount-VHD](https://learn.microsoft.com/en-us/powershell/module/hyper-v/mount-vhd?view=windowsserver2025-ps).
2. For a generation 2 guest, use GPT with a FAT32 EFI system partition, a 16 MB MSR, and an NTFS Windows partition. Current Microsoft guidance specifies an ESP minimum of 200 MB for 512/512e sectors and 300 MB for 4K native sectors; choosing at least 300 MB avoids the older 100 MB sample assumption. Microsoft's full layout also includes a recovery partition after Windows. If recovery is omitted for a disposable lab, record that reduced layout rather than claiming a complete recovery deployment. [UEFI/GPT partition guidance](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/configure-uefigpt-based-hard-drive-partitions?view=windows-11).
3. Enumerate the WIM, then apply the selected image to the new Windows partition. The core contract is `DISM /Apply-Image /ImageFile:<install.wim> /Index:<verified-index> /ApplyDir:<new-Windows-volume> /CheckIntegrity /Verify`. `/CheckIntegrity` detects WIM corruption during apply; `/Verify` checks errors and duplication. Check native process exit codes before proceeding. [DISM image management](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism-image-management-command-line-options-s14?view=windows-11).
4. Use deployment tools compatible with the image. Microsoft's DISM guidance explicitly distinguishes the host environment from the target image and describes installing newer deployment tools from the ADK when needed. Record the DISM/BCDBoot versions; do not infer compatibility only from the host's friendly OS name. [DISM supported platforms](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism-supported-platforms?view=windows-11).
5. Populate boot files with `bcdboot <new-Windows-volume>\Windows /s <new-ESP>: /f UEFI`. The explicit `/s` is essential on a running host: it directs the boot files and BCD store to the new disk and suppresses creation of a host NVRAM Windows Boot Manager entry. `/f UEFI` requires `/s`; the fallback EFI path is `\EFI\Boot\bootx64.efi`. Verify both source and target belong to the new VHDX before invocation. Do not follow native-VHD-boot instructions that add the image to the host boot menu. [BCDBoot options](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/bcdboot-command-line-options-techref-di?view=windows-11).
6. Put the fresh per-guest answer file at `<new-Windows-volume>\Windows\Panther\unattend.xml`, then detach the disk before guest startup. Microsoft documents replacing an answer file in an offline image and discovery at the beginning of each configuration pass. Do not reuse a cached answer file from an already booted VM: Setup annotates processed passes. Remove residual answer files only after their required passes complete. [Windows Setup automation](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-automation-overview?view=windows-11).

Use component names and passes from the image's Windows SIM catalog. Microsoft directs users to load the image into Windows SIM to determine component applicability; desktop unattend examples alone do not certify every setting on a particular Core build. [Shell-Setup applicability](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-shell-setup).

## PowerShell Direct and readiness

PowerShell Direct supports Windows Server 2016 and later guests on a local Hyper-V host running Windows 10/Server 2016 or later, regardless of guest network/remoting configuration. The guest must be running with at least one configured user profile; the host user must be a Hyper-V administrator and supply valid guest credentials. Use `Invoke-Command -VMId <owned-id> -Credential <guest-credential>` and persistent `New-PSSession` sessions for `Copy-Item -ToSession/-FromSession`. Explicit credentials also avoid an older documented service-hang bug. `-RunAsAdministrator` is not a VM connection parameter. [PowerShell Direct](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/powershell-direct).

Implementation implications: use bounded polling for a successful command that reports the expected computer name and completed bootstrap marker, not just Hyper-V's Running state or a fixed sleep. Recreate sessions after reboots. Before promotion use the machine's local Administrator identity; after promotion use the domain identity. Persist operation intent before a restart, then verify resulting state before retrying. A lost remoting connection during promotion is not proof of promotion failure or success.

## AD DS creation and member join

Install the `AD-Domain-Services` feature with management tools inside each future DC, then use `ADDSDeployment`. The role installation is separate from promotion. Microsoft provides `Test-ADDSForestInstallation`, `Test-ADDSDomainInstallation`, and `Test-ADDSDomainControllerInstallation` to run prerequisites. Keep prerequisite checks enabled. [AD DS installation workflow](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/deploy/install-active-directory-domain-services--level-100-).

For the first DC, the important `Install-ADDSForest` arguments are the DNS `-DomainName`, explicit `-DomainNetbiosName`, `-InstallDns`, functional levels, and a `SecureString` `-SafeModeAdministratorPassword`. This password is for DSRM, not the regular domain account. For an isolated new root with no parent DNS delegation, explicitly choose `-CreateDnsDelegation:$false`. `-Force` suppresses confirmation; it is not equivalent to `-SkipPreChecks`. The cmdlet normally reboots; `-NoRebootOnCompletion` leaves the machine in an incomplete role state until reboot and needs deliberate orchestration. [Install-ADDSForest](https://learn.microsoft.com/en-us/powershell/module/addsdeployment/install-addsforest?view=windowsserver2025-ps).

For DC2, configure its DNS client to DC1 before promotion. Use `Install-ADDSDomainController -DomainName <existing-domain> -Credential <domain-admin> -InstallDns -ReplicationSourceDC <dc1-FQDN> -SafeModeAdministratorPassword <secure-string>`. The default parameter set creates a writable DC; do not supply `-ReadOnlyReplica` or `-NoGlobalCatalog`. `-AllowDomainControllerReinstall` bypasses the existing-name safeguard and is inappropriate for automatic retry. Wait for promotion/reboot and replication before treating DC2 as an available DNS or write target. [Install-ADDSDomainController](https://learn.microsoft.com/en-us/powershell/module/addsdeployment/install-addsdomaincontroller?view=windowsserver2025-ps).

On the member, run Windows PowerShell `Add-Computer -DomainName <domain> -Credential <join-credential> -Restart -PassThru` after DNS resolution works. `-Credential` authorizes the domain join; `-LocalCredential` is for connecting to a remote target and is unnecessary when the command already runs inside the guest through PowerShell Direct. `-OUPath` is a distinguished name, not a DNS name. A restart makes membership effective. [Add-Computer](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/add-computer?view=powershell-5.1).

Use a post-restart acceptance check, not only a successful installation return: expected domain/forest identities, both DC records with `IsReadOnly=false`, ADWS/NTDS/DNS running, SYSVOL and NETLOGON ready, RootDSE synchronized state, replication partners without failures, and member domain membership plus secure-channel validation. Seed a disposable object on one writable DC and observe it on the other to establish actual replication before collecting comparison fixtures. These are proposed acceptance criteria, not claims that the current host has passed them. [Get-ADRootDSE](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-adrootdse?view=windowsserver2025-ps), [AD replication cmdlets](https://learn.microsoft.com/en-us/powershell/module/activedirectory/?view=windowsserver2025-ps).

## Version profiles and functional levels

| Guest DC versions | Suitable functional level | Consequence |
| --- | --- | --- |
| 2016, 2019, 2022, or a mixture including 2025 | 2016 | Supports all four requested releases. 2019 and 2022 have no separate functional levels. |
| Only 2025 | 2016 or 2025 | Raising to 2025 prevents adding 2016/2019/2022 DCs. Keep the compatibility profile separate from a 2025 feature profile. |

Functional levels constrain DC operating systems, not ordinary member operating systems. Server 2025 DCs cannot join at the 2012 R2 functional level. [Current interoperability matrix](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/active-directory-functional-levels).

The `Install-ADDSForest` reference still lists `WinThreshold`/integer `7` as 2016 and omits the newer enum in its accepted-values list. Do not mistake that documentation gap for absence of the 2025 level. Inspect the installed command's parameter types/enum values and record actual post-promotion levels. The current 2025 release notes identify the new unattended numeric level as `10`, and require at least 2016 for new forests/configuration sets and for promoting 2025 replicas. [Install-ADDSForest parameter reference](https://learn.microsoft.com/en-us/powershell/module/addsdeployment/install-addsforest?view=windowsserver2025-ps), [Server 2025 AD changes](https://learn.microsoft.com/en-us/windows-server/get-started/whats-new-windows-server-2025).

## Native command and fixture inventory

Collect the native API inventory **inside each OS profile**, preferably in Windows PowerShell 5.1, after importing the local ActiveDirectory module. `Get-Command -Module ActiveDirectory -CommandType Cmdlet` describes the installed cmdlets rather than the latest web documentation. Project stable fields from `CommandInfo`, `Parameters` and `ParameterSets`: name, module name/version, implementing assembly version, output types, parameter name/type, aliases, mandatory status, position, pipeline binding and set membership. Enumerate enum names and validation attributes where present. Include OS build, architecture and PowerShell version in the envelope. [Get-Command](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/get-command?view=powershell-7.5).

Serialize those projections rather than the whole reflection object graph. `ConvertTo-Json` defaults to depth 2, so choose an explicit depth sufficient for parameter sets and preserve collections as arrays even when empty or singleton. Sort commands, sets and parameters for reproducible diffs. Serialize in the guest before copying the artifact to avoid losing type details to remoting serialization. These are collector design choices based on the serializer's documented behavior. [ConvertTo-Json](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/convertto-json?view=powershell-5.1).

For directory fixture inventories, specify the exact DC with `-Server`, discover naming contexts using `Get-ADRootDSE`, and query required partitions explicitly. `Get-ADObject` returns a limited property set unless `-Properties` is supplied, supports paging, and separates `-LDAPFilter` from PowerShell-expression `-Filter`. AD LDS queries need an explicit instance endpoint such as `member:51300`, with a partition/search base when no default is configured. Avoid `Format-Table` output as machine-readable evidence. [Get-ADRootDSE](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-adrootdse?view=windowsserver2025-ps), [Get-ADObject](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-adobject?view=windowsserver2025-ps).

Keep capabilities, successful cases, unsupported commands, missing prerequisites and unexpected failures distinct. Record the actual command name, target server and sanitized error identifier per failure; an empty result is not equivalent to unsupported behavior. Select nonsecret properties rather than broadly exporting credentials or managed-password attributes. For a new lab, preserve generated SIDs/GUIDs in run artifacts while normalizing them only in explicit comparison fixtures.

## Staged expansion profiles

### Child domain

Add a separate guest and create a new child domain with `Install-ADDSDomain -DomainType ChildDomain -ParentDomainName <parent-FQDN> -NewDomainName <single-child-label>`, forest-authorized credentials, DNS and DSRM settings. The new label is not the complete child FQDN. The parent DNS zone exists in this scenario, so DNS delegation is appropriate after checking permissions and name collisions. Verify the child domain, parent-child trust, GC discovery and forest replication before seeding cross-domain fixtures. [Install-ADDSDomain](https://learn.microsoft.com/en-us/powershell/module/addsdeployment/install-addsdomain?view=windowsserver2025-ps).

### Second forest and forest trust

Create a genuinely separate forest on another guest. Configure reciprocal DNS conditional forwarders to its lab DC addresses. For an AD-integrated forwarder, use an appropriate `-ReplicationScope`; omit recursion fallback for the isolated namespace. Do not replace an existing authoritative zone with a forwarder. [DNS forwarding](https://learn.microsoft.com/en-us/windows-server/networking/dns/configure-dns-forwarding).

**Do not use `netdom trust /add /foresttransitive` as a forest-trust creation recipe.** Microsoft explicitly states that `netdom trust` cannot create a trust between two AD DS forests. [netdom trust](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netdom-trust).

The documented .NET `System.DirectoryServices.ActiveDirectory.Forest.CreateTrustRelationship(targetForest, direction)` creates both sides in one call; construct authenticated contexts for each lab forest and choose the direction explicitly. Treat existence as a reconciliation case, not an instruction to recreate or remove a trust. Verify the resulting trust's forest-transitive property and direction on both sides, then test an intended cross-forest authentication path. [Forest.CreateTrustRelationship](https://learn.microsoft.com/en-us/dotnet/api/system.directoryservices.activedirectory.forest.createtrustrelationship?view=windowsdesktop-9.0).

### Read-only domain controller

An RODC is an additional guest in an existing domain, not the first DC. Direct promotion uses `Install-ADDSDomainController -ReadOnlyReplica`; that parameter set requires `-SiteName`. Supply a real existing site, domain credentials, replication source and DSRM password. Keep password replication permissions restricted to disposable test principals. [Install-ADDSDomainController](https://learn.microsoft.com/en-us/powershell/module/addsdeployment/install-addsdomaincontroller?view=windowsserver2025-ps).

To exercise delegation, stage its account using `Add-ADDSReadOnlyDomainControllerAccount`, then attach the correctly named guest using `Install-ADDSDomainController -UseExistingAccount`. Do not mix the direct-promotion and staged-account parameter sets. Test read-only write rejection and password replication policy as separate capabilities. [RODC staged workflow](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/deploy/rodc/install-a-windows-server-2012-active-directory-read-only-domain-controller--rodc---level-200-).

### Replicated AD LDS

Install the `ADLDS` feature on member guests and create instances with `ADAMInstall.exe /answer:<file>`. Microsoft's current example confirms `[ADAMInstall]`, `InstallType=Unique`, instance name, local LDAP/SSL ports, application partition DN, data/log paths and service-account settings. LDAP/LDAPS ports must avoid AD DS conflicts if installed on a DC. Prefer member guests and explicit nondefault ports for this lab. Certificates need a trusted name and private-key access for the service identity when testing LDAPS. [Microsoft AD LDS setup example](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/on-premises-ldap-connector-prepare-directory).

A replicated pair must belong to the **same configuration set**; creating two Unique instances does not establish replication. The Microsoft Directory Services team documents adding instances to an existing set and checking replication with an instance-specific `repadmin /showreps server:port`. AD LDS has Naming Master and Schema Master roles; it does not have the full set of five AD DS FSMO roles. [Microsoft Directory Services team](https://techcommunity.microsoft.com/blog/askds/how-to-decommission-an-adamadlds-server-and-add-additional-servers/397218).

The precise unattended replica-answer keys were not established from the accessible primary pages in this research. Before implementation, read the guest's installed ADAMInstall help/sample answer file or export the wizard's answer file, then verify replica source, source LDAP port, credentials, partition selection and service identity on that OS build. Do not transplant `DCPROMO`'s `ReplicaOrNewDomain` fields into an ADAMInstall answer file. Server 2025 also requires the configuration-set functional level to be at least 2016. [Server 2025 prerequisites](https://learn.microsoft.com/en-us/windows-server/get-started/whats-new-windows-server-2025).

Do not clone a running AD LDS instance or independently restore one replica as an ordinary fixture reset. Microsoft's virtualization guidance warns that AD LDS lacks VM-Generation-ID awareness and copying/restoring it can introduce USN rollback divergence. Rebuild disposable instances from a clean pre-directory image and reseed, or use an application-aware backup/recovery procedure. [AD DS virtualization guidance, AD LDS caveat](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh831734(v=ws.11)).

### Server 2025 delegated managed service accounts

At least one Server 2025 DC must be discoverable by the member; a schema extension plus a 2025 member alone is insufficient. All hosts involved in a migrated workload must run a dMSA-supported OS. The FAQ excludes migration from gMSA to dMSA and merging several service accounts into one dMSA. Preserve the original account after migration because of the links and service configuration. [dMSA FAQ](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/delegated-managed-service-accounts/delegated-managed-service-accounts-faq).

Use a disposable standalone dMSA first, with the native `New-ADServiceAccount -CreateDelegatedServiceAccount` capability and explicit `DNSHostName`, AES encryption and allowed host principals. The setup guide requires a KDS root key, appropriate AD permissions and client `DelegatedMSAEnabled` configuration. Interpretation for this lab: its two-way forest-trust prerequisite concerns the described cross-forest scenarios; the standalone same-domain workflow does not require constructing a second forest. Validate this interpretation in the dedicated dMSA profile. [New-ADServiceAccount](https://learn.microsoft.com/en-us/powershell/module/activedirectory/new-adserviceaccount?view=windowsserver2025-ps), [dMSA setup](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/delegated-managed-service-accounts/delegated-managed-service-accounts-set-up-dmsa).

For the two-DC profile, account for KDS replication and activation delay. Microsoft's KDS guidance describes the up-to-10-hour convergence period and limits its backdated-key shortcut to a single-DC test environment. Do not assume copying the dMSA page's backdated example makes a two-DC environment ready: verify the same key on both DCs and use the documented wait unless deliberately testing a validated shortcut. Do not delete/recreate existing root keys as a retry. [KDS root-key guidance](https://learn.microsoft.com/en-us/windows-server/security/group-managed-service-accounts/create-the-key-distribution-services-kds-root-key).

## Existing Hyper-V discovery anomaly

The supplied host observation is that elevated `Get-VM` fails with ObjectNotFound while direct CIM enumeration of `Msvm_ComputerSystem` and `Get-VMSwitch` work. This research does **not** establish a cause or prove module corruption. Microsoft's v2 CIM model represents both the hosting computer and VMs; distinguish them by `Caption`, and use `Name` as the VM GUID rather than treating the display `ElementName` as a unique identifier. [Msvm_ComputerSystem v2](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-computersystem).

Read-only diagnostic sequence: compare `Get-Command Get-VM -All` and module path/version in fresh `powershell.exe -NoProfile` and `pwsh -NoProfile`; inspect available Hyper-V versions; try module-qualified `Hyper-V\Get-VM` and a known VM GUID; compare CIM IDs with each returned object; collect the full error record and Hyper-V management event logs. A command-name/module collision, version mismatch or per-VM association issue remains a hypothesis until one of these observations distinguishes it. Microsoft lists modern Hyper-V modules as natively compatible with PowerShell 7, so PowerShell 7 alone is not evidence of an unsupported setup. [Module compatibility](https://learn.microsoft.com/en-us/powershell/windows/module-compatibility?view=windowsserver2019-ps), [Command resolution inventory](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/get-command?view=powershell-7.5).

A working CIM read is useful for collision detection; it is not authorization to alter existing registrations. Do not unregister, reset, remove, repair or recreate existing VMs as part of lab setup. Establish reliable access to each newly owned VM before continuing with operations that depend on Hyper-V cmdlet objects.

The teardown qualification reproduced a related failure twice with elevated
`Get-VMNetworkAdapter -All` after the owned lab VMs had been removed. Direct
switch lookup, CIM switch lookup, configured-connection enumeration, and live
port enumeration still succeeded. This narrows the failure to host-wide
Hyper-V object enumeration; it does not establish which unrelated object or
association caused it.

Removal therefore checks the exact owned switch's live ports through
`Msvm_SystemDevice` and its configured connections through
`Msvm_EthernetPortAllocationSettingData.HostResource`. Both checks matter:
configured connections protect stopped VMs even if no live port exists.
A live diskless, stopped probe VM blocked removal, while an empty switch
passed. Query failures and malformed switch references fail closed. See
[Microsoft's switch-port enumeration example](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/querying-networking-objects)
and the [connection allocation model](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-ethernetportallocationsettingdata).
